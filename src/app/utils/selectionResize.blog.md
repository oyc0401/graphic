# 선택창 리사이즈 개발 메모

선택창을 개발하고 있다.

내가 만들고 있는 것은 비트맵 에디터의 선택 도구다. 사용자는 먼저 캔버스에서 구역을 선택한다. 그 다음 선택된 구역의 핸들을 잡고 늘리거나 줄일 수 있어야 한다. Shift를 누른 상태로 움직이면 원래 선택 영역의 비율이 유지되어야 하고, 핸들을 반대쪽으로 넘기면 선택된 이미지가 뒤집히는 것도 가능해야 한다.

기능을 말로 쓰면 단순하다. 선택하고, 크기를 바꾸고, 비율을 유지하고, 뒤집는다. 하지만 실제로 구현하려고 하니 이 네 가지가 한꺼번에 얽혔다. 특히 비트맵 에디터에서는 1픽셀 단위로 결과가 보이기 때문에, 선택창이 한 칸만 어긋나도 바로 이상하게 느껴진다.

처음에는 선택창을 이런 형태로 구현했다.

```ts
let { x, y, w, h } = this.start;
let finalFlipH = this.start.flipH;
let finalFlipV = this.start.flipV;

switch (this.activeHandle) {
  case "RB":
    w = pointer.x - x + 1;
    h = pointer.y - y + 1;
    if (w < 0) finalFlipH = !this.start.flipH;
    if (h < 0) finalFlipV = !this.start.flipV;
    break;

  case "LT":
    w = x + w - pointer.x;
    h = y + h - pointer.y;
    x = pointer.x;
    y = pointer.y;
    if (w < 0) finalFlipH = !this.start.flipH;
    if (h < 0) finalFlipV = !this.start.flipV;
    break;

  case "R":
    w = pointer.x - x + 1;
    if (w < 0) finalFlipH = !this.start.flipH;
    break;
}

if (shiftKey) {
  const ratio = this.start.w / this.start.h;

  if (["L", "R"].includes(this.activeHandle)) {
    h = Math.floor(Math.abs(w) / ratio);
  } else if (["T", "B"].includes(this.activeHandle)) {
    w = Math.floor(Math.abs(h) * ratio);
  }
}
```

핸들 종류를 보고 `switch`로 분기했다. 예를 들어 오른쪽 아래 핸들을 잡으면 오른쪽과 아래쪽을 늘리고, 왼쪽 위 핸들을 잡으면 x, y, width, height를 같이 바꾸는 식이었다. 여기에 Shift를 누른 경우에는 비율 계산을 추가하고, 포인터가 반대 방향으로 넘어가면 flip 값을 바꾸는 로직을 붙였다.

처음에는 이 방식이 가장 직접적이라고 생각했다. 핸들이 8개니까 8개 방향을 나누고, 각 방향마다 필요한 계산을 적으면 된다고 생각했다. 실제로 작은 케이스에서는 잘 동작하는 것처럼 보였다.

하지만 이렇게 개발하다 보니 너무 버그가 일어나기 쉬웠다.

핸들 방향마다 조건이 갈라지고, Shift를 눌렀는지에 따라 또 조건이 갈라지고, 뒤집기까지 들어가니 코드가 금방 복잡해졌다. 어떤 핸들은 x를 바꿔야 하고, 어떤 핸들은 y를 바꿔야 하고, 어떤 핸들은 width만 바꾸면 되지만, 어떤 핸들은 width와 height를 동시에 바꿔야 했다.

여기에 비율 유지가 들어가면 더 헷갈렸다. width를 기준으로 height를 바꿔야 하는지, height를 기준으로 width를 바꿔야 하는지 매번 달랐다. 뒤집기까지 들어가면 포인터가 기준점을 넘어간 순간부터 계산 방향이 바뀐다. 이렇게 되니 코드를 읽어도 이 결과가 맞는지 확신하기 어려웠다.

무엇보다 문제는 확인이 어려웠다는 점이다. 화면에서 드래그해보며 “대충 맞는 것 같다”고 느끼는 것과, 모든 경우가 정확히 맞는 것은 다르다. 한 케이스를 고치면 다른 방향에서 깨질 수 있었다. 그래서 선택창 리사이즈 계산을 화면에서 직접 확인하는 방식으로만 개발하면 안 되겠다고 생각했다.

그래서 테스트 가능한 코드를 만들었다.

먼저 테스트 구조를 짰다. 흔히 TDD라고 부르는 방법인데, 나는 여기서 특히 interface를 예쁘게 선언하는 것이 중요하다고 생각했다. 나중에 실제 선택 도구에서 쓰기에도 좋아야 하고, 테스트만 읽어도 어떤 계산을 하는지 이해할 수 있어야 했다.

내가 원한 형태는 이런 식이었다. 어떤 사각형이 있고, 어떤 핸들을 잡고, 포인터가 어디로 이동했을 때, 결과가 어떻게 나와야 하는지 그대로 드러나는 형태다.

```ts
expect(
  resizeSelectionFromHandle({
    startRect: { x: 2, y: 2, width: 5, height: 5 },
    handle: "RB",
    pointer: { x: 5, y: 4 },
    keepRatio: false,
  }),
).toEqual({ x: 2, y: 2, width: 4, height: 3, flipH: false, flipV: false });
```

이렇게 만들면 테스트가 단순한 검증 코드가 아니라 설명이 된다. `startRect`를 보면 시작 선택창을 알 수 있고, `handle`을 보면 사용자가 어디를 잡았는지 알 수 있고, `pointer`를 보면 어디까지 드래그했는지 알 수 있다. 그리고 `toEqual`을 보면 결과 선택창이 어떻게 바뀌어야 하는지 바로 보인다.

이 방식이 좋았던 이유는 머릿속으로만 계산하지 않아도 된다는 점이었다. 선택창 리사이즈는 계속 헷갈린다. 포인터가 있는 칸을 포함하는지, 끝 좌표가 포함되는지, 뒤집힌 상태에서는 x와 y가 어디가 되는지 자꾸 다시 생각하게 된다. 그래서 테스트에 입력과 결과를 명시적으로 적어두는 것이 필요했다.

테스트를 작성하기 위해 경우의 수를 직접 그려보며 따져가며 테스트를 추가했다.

```md
TODO: 여기에 나중에 노트 사진 붙여넣기
```

종이에 사각형을 그리고, 시작점과 끝점을 표시하고, 핸들을 잡고 움직였을 때 어떤 칸들이 선택창에 포함되어야 하는지 하나씩 따져봤다. 말로는 “오른쪽 아래 핸들을 안쪽으로 옮긴다”지만, 실제로는 몇 칸이 포함되는지를 직접 세어봐야 했다.

이 과정에서 좌표계가 중요하다는 것을 다시 느꼈다. 선택창은 선이 아니라 픽셀 칸의 묶음이다. 그래서 포인터가 위치한 칸이 포함되는지 여부가 중요하다. 테스트를 쓰기 전에는 이 부분이 계속 흐릿했는데, 직접 그려보면서 케이스를 추가하니 기준이 조금씩 선명해졌다.

그런데 이렇게 개발한다고 해도 내부적으로 `if`, `switch`를 사용해서 코드가 복잡해지는 것을 느꼈다.

테스트를 만들었기 때문에 결과가 틀리면 잡아낼 수는 있었다. 하지만 구현 자체가 여전히 복잡하면 새로운 케이스를 추가할 때마다 내부 조건이 계속 늘어날 수밖에 없었다. 핸들별로 계산식을 따로 두는 방식은 결국 같은 개념을 여러 방향으로 복사해서 쓰는 느낌이었다.

이때 포인터가 속한 영역은 필수적으로 선택창에 포함된다는 것을 떠올렸다.

처음에는 핸들 방향별로 width와 height를 어떻게 바꿀지 생각했다. 그런데 관점을 바꾸면 더 단순했다. 포인터가 있는 칸은 무조건 선택창에 들어와야 한다. 그러면 리사이즈 결과는 포인터를 포함하는 어떤 사각형이어야 한다.

그리고 앵커와 포인터는 무조건 꼭짓점, 즉 모서리에 속한다는 것을 생각해냈다.

코너 핸들을 잡고 움직인다고 생각하면 더 명확하다. 사용자가 잡지 않은 반대쪽 꼭짓점은 고정된 앵커가 된다. 사용자가 움직이는 포인터는 새 꼭짓점이 된다. 결국 선택창은 앵커와 포인터를 두 꼭짓점으로 하는 사각형이다.

예를 들어 RB 핸들을 잡으면 왼쪽 위가 앵커다. LT 핸들을 잡으면 오른쪽 아래가 앵커다. RT 핸들을 잡으면 왼쪽 아래가 앵커고, LB 핸들을 잡으면 오른쪽 위가 앵커다. 포인터가 어느 방향으로 움직이든 앵커와 포인터가 사각형의 두 모서리가 된다.

이렇게 생각하니 이전보다 훨씬 단순해졌다. x, y, width, height를 핸들별로 억지로 계산하는 것이 아니라, 앵커와 포인터가 만드는 사각형을 구하면 된다. 포인터가 앵커를 지나가면 사각형은 여전히 만들 수 있고, 그때 flip 상태만 바꾸면 된다.

그래서 앵커 기반 알고리즘을 개발해서 재구성했다.

핸들별로 “어떤 점이 앵커인가”를 먼저 정한다. 그 다음 앵커와 포인터를 기준으로 inclusive 사각형을 만든다. 이 사각형은 항상 양수 width와 height를 가진다. 포인터가 앵커를 넘어갔는지는 따로 판단해서 flip 값을 정한다.

```ts
function getOppositeCornerAnchor(startRect, handle) {
  const right = startRect.x + startRect.width - 1;
  const bottom = startRect.y + startRect.height - 1;

  return {
    x: handle.includes("L") ? right : startRect.x,
    y: handle.includes("T") ? bottom : startRect.y,
  };
}

function rectFromInclusiveCorners(anchor, pointer) {
  const horizontal = inclusiveRange(anchor.x, pointer.x);
  const vertical = inclusiveRange(anchor.y, pointer.y);

  return {
    x: horizontal.start,
    y: vertical.start,
    width: horizontal.size,
    height: vertical.size,
  };
}
```

이 방식으로 바꾸니 코드가 훨씬 설명 가능해졌다. 이전에는 핸들마다 계산식이 흩어져 있었다면, 이제는 공통 규칙이 생겼다.

앵커와 포인터가 사각형을 만든다.

포인터가 있는 칸은 포함된다.

포인터가 앵커를 지나가면 flip이 된다.

Shift를 누르면 그 사각형을 기준으로 비율을 유지한다.

이 규칙만 이해하면 각 케이스를 훨씬 쉽게 설명할 수 있었다.

이렇게 개발하니 버그가 없는 선택창이 완성되었다.

물론 처음부터 한 번에 맞춘 것은 아니다. 테스트를 추가하면서 기대값을 고치기도 했고, 내가 잘못 생각한 부분을 다시 계산하기도 했다. 하지만 중요한 점은 이제 버그를 화면에서 감으로 찾는 것이 아니라, 작은 입력과 결과로 재현할 수 있게 되었다는 것이다.

결과적으로 선택창 리사이즈는 단순히 `switch`를 잘 쓰는 문제가 아니었다. 어떤 점이 고정되고, 어떤 점이 움직이고, 어떤 칸이 포함되어야 하는지를 명확히 하는 문제였다. 앵커와 포인터라는 관점으로 바꾸고 나서야 로직이 안정되기 시작했다.
