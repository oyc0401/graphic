# 선택창 리사이즈 작업 일기

이 문서는 그대로 블로그에 올릴 글이 아니다. 나중에 글을 쓸 때 놓치고 싶지 않은 생각, 헷갈렸던 지점, 중간에 바뀐 판단을 남겨두기 위한 작업 일기다.

## 시작점

비트맵 에디터를 만들고 있는데, 선택창 리사이즈가 계속 마음에 걸렸다.

선택 영역을 만들고, 핸들을 잡고, 크기를 바꾸고, Shift를 누르면 비율을 유지하고, 반대쪽으로 넘기면 도형이 뒤집히는 기능이다. 겉으로 보기에는 흔한 기능이다. 대부분의 그래픽 툴에서 너무 자연스럽게 동작하기 때문에 처음에는 그렇게 어려운 문제라고 생각하지 않았다.

하지만 직접 구현해보니 작은 버그가 계속 생겼다.

- 포인터가 있는 칸이 선택창에 포함되지 않는 느낌
- 한 칸 덜 잡히거나 한 칸 더 잡히는 문제
- Shift를 누르면 기준점이 이상하게 밀리는 문제
- 핸들을 반대쪽으로 넘겼을 때 flip 상태가 예상과 다르게 바뀌는 문제
- 이미 뒤집힌 상태에서 다시 조절하면 상태가 더 헷갈리는 문제

비트맵 에디터에서는 이런 문제가 더 크게 느껴진다. 벡터 도형이면 조금 덜 티 날 수도 있지만, 픽셀 단위 선택창은 1칸 차이가 바로 보인다. 사용자가 포인터를 둔 칸이 선택 영역에 포함되지 않으면 “내가 찍은 곳이 왜 안 잡히지?”라는 느낌이 든다.

## 기존 코드에서 답답했던 점

문제는 `SelectionTool` 안에 너무 많은 것이 섞여 있었다는 점이다.

한 파일 안에 포인터 이벤트 처리, 히트테스트, 커서 변경, 선택창 이동, 선택창 리사이즈 계산, Shift 비율 유지, flip 계산, MobX 상태 갱신, worker 호출이 같이 있었다.

버그를 볼 때 내가 정말 보고 싶은 것은 “이 핸들을 잡고 이 포인터로 움직이면 다음 rect가 뭐지?”였다. 그런데 실제 코드를 보면 이벤트 처리와 상태 반영까지 같이 읽어야 했다. 계산만 떼어놓고 생각하기 어려웠다.

특히 Shift와 flip이 같이 들어가면 코드를 읽어도 확신이 잘 안 생겼다. 한 군데를 고치면 다른 핸들이 깨질 것 같았다. 그래서 바로 고치기보다 먼저 계산을 격리해야겠다고 생각했다.

## 순수 함수로 빼자는 판단

선택창 리사이즈는 결국 이렇게 말할 수 있다.

드래그 시작 시점의 선택창, 잡은 핸들, 현재 포인터 위치, Shift 여부가 주어졌을 때 다음 선택창은 무엇인가?

이 질문에 답하는 순수 함수가 있으면 좋겠다고 생각했다. 그래서 `resizeSelectionFromHandle`을 만들었다.

이 함수는 UI를 모른다.

- DOM `PointerEvent`를 모른다.
- MobX `selection` 상태를 모른다.
- worker 호출을 모른다.
- 화면 좌표 변환도 모른다.

입력은 `startRect`, `handle`, `pointer`, `keepRatio`, `allowFlip`, 시작 flip 상태 정도다. 출력은 `x`, `y`, `width`, `height`, `flipH`, `flipV`다.

이렇게 만들고 나니 리사이즈 문제를 UI 문제가 아니라 좌표 계산 문제로 볼 수 있게 되었다.

## 처음 잡은 핵심 규칙

처음부터 가장 중요했던 규칙은 이것이었다.

포인터가 위치한 칸은 결과 선택창 안에 포함되어야 한다.

이 문장을 기준으로 삼았다.

예를 들어 `x=2, y=2, width=5, height=5`라면 오른쪽 아래 끝은 `(6, 6)`이다. `(7, 7)`이 아니다. 이건 inclusive 좌표계다. width와 height는 픽셀 칸 개수이고, 끝 칸은 포함된다.

그래서 RB 핸들을 잡고 포인터가 `(6, 6)`에 있으면 선택창은 변하지 않아야 한다. 포인터가 `(6, 4)`로 가면 높이는 3이 되어야 한다. 포인터가 `(8, 9)`로 가면 그 칸까지 포함되도록 늘어나야 한다.

이 규칙을 말로 쓰기 전에는 계속 헷갈렸다. 테스트를 쓰면서 이 문장이 기준이 되었다.

## 테스트 이름을 신중하게 쓰기로 함

테스트 이름도 중요했다.

처음에는 단순히 케이스를 추가하는 느낌이었는데, 곧 테스트 파일 자체가 정책 문서가 되어야 한다고 생각했다. 나중에 이 파일을 읽었을 때 “왜 이런 기대값이지?”를 다시 계산하지 않아도 되게 만들고 싶었다.

그래서 테스트 이름을 대충 쓰지 않기로 했다.

나쁜 이름:

- `RB resize`
- `works`
- `resize smaller`

원하는 이름:

- `포인터가 기존 오른쪽 아래 끝 칸에 그대로 있으면 선택창의 위치와 크기는 변하지 않는다`
- `포인터가 안쪽 칸으로 이동하면 그 칸까지 선택창이 줄어든다`
- `포인터가 기존 왼쪽 위 끝을 지나가면 flipH와 flipV가 켜진다`

테스트 이름이 길어져도 괜찮다고 판단했다. 이 테스트는 실행만 하는 코드가 아니라, 나중에 내가 다시 읽을 설명서이기도 하다.

## keepRatio=false부터 시작

처음에는 Shift를 생각하지 않고 `keepRatio=false`만 테스트했다.

이 단계의 목표는 자유 리사이즈의 기본 좌표계를 고정하는 것이었다.

테스트한 상황:

- 정지상태
- 줄어들기
- 늘어나기
- 너비 또는 높이가 1칸이 되는 경우
- 코너 핸들에서는 너비와 높이가 모두 1칸이 되는 경우

처음에는 모든 방향을 다 만들기보다 RB부터 시작했다. RB가 가장 직관적이기 때문이다. 왼쪽 위가 고정되고 오른쪽 아래가 포인터를 따라간다.

그다음 8방향으로 확장했다. 이때도 모든 숫자를 작게 유지했다. `999` 같은 값은 테스트를 읽기 어렵게 만든다. 좌표가 50을 넘어가지 않게 바꾸면서 눈으로 계산 가능한 테스트를 만들었다.

## 포맷도 테스트 가독성에 영향을 줌

테스트 기대값 객체는 한 줄로 유지하고 싶었다.

```ts
{ x: 2, y: 2, width: 5, height: 5, flipH: false, flipV: false }
```

이 형태가 선택창 결과를 한눈에 보기 좋았다. 여러 줄로 풀리면 읽는 흐름이 끊겼다.

Biome 설정에서 `.test.ts`에 `lineWidth`를 넉넉하게 줬지만, Biome이 이미 여러 줄인 객체를 자동으로 한 줄로 접어주지는 않았다. 결국 기대값은 직접 한 줄로 정리했다. 이것도 나중에 글감으로 쓸 수 있다. 포맷터 설정만으로 원하는 읽기 형태가 항상 나오지는 않는다.

## flip 테스트

다음으로 flip을 테스트했다.

핸들을 반대쪽 기준점 너머로 넘기면 도형이 뒤집혀야 한다. 이때 `width`나 `height`가 음수가 되면 안 된다. 위치는 정규화되어야 하고, flip 상태가 바뀌어야 한다.

중요한 점은 시작 flip 상태다.

기본 상태에서 crossing이 발생하면 flip이 켜진다. 하지만 이미 flip이 켜진 상태에서 crossing이 발생하면 flip이 꺼져야 한다. 즉 flip은 현재 포인터 위치만으로 정하는 값이 아니라 시작 flip 상태에서 토글되는 값이다.

그래서 테스트를 둘로 나눴다.

- `도형을 뒤집으면 flip이 된다. (기본 상태)`
- `도형을 뒤집으면 flip이 된다. (초기 flip 상태)`

이 두 섹션은 일부러 나눴다. 나중에 읽을 때 “처음부터 flip이 켜져 있던 경우”를 따로 생각할 수 있어야 하기 때문이다.

## allowFlip=false

flip을 막아야 하는 경우도 있었다.

`allowFlip=false`라면 포인터가 반대 anchor를 지나가도 선택창은 뒤집히면 안 된다. 대신 1칸 크기에서 멈춘다.

이 옵션은 처음에는 핵심 기능처럼 보이지 않았지만, 실제 도구에서는 필요하다. 어떤 상황에서는 사용자가 크기를 줄이고 싶을 뿐 도형을 뒤집고 싶지 않을 수 있다. 그래서 이 정책도 순수 함수 입력으로 넣고 테스트했다.

## Shift 비율 유지

그다음이 Shift였다.

`keepRatio=true`이면 시작 선택창의 비율을 유지해야 한다. 처음에는 width가 바뀌면 height를 비율에 맞춰 바꾸면 된다고 생각했다. 하지만 실제로는 기준점, 포인터 포함, 중심 유지, flip 여부가 같이 걸렸다.

엣지 핸들에서는 한 축만 직접 움직인다. 예를 들어 R 핸들은 width가 바뀐다. Shift 상태라면 height도 시작 비율에 맞게 바뀌어야 한다. 이때 세로 중심을 유지해야 자연스럽다.

B 핸들은 반대로 height가 바뀌고 width가 따라온다. 이때는 가로 중심을 유지해야 한다.

코너 핸들은 조금 다르다. 반대쪽 꼭짓점이 anchor가 되고, 포인터와 anchor가 만든 inclusive 사각형을 기준으로 부족한 축을 확장한다.

## Shift + flip이 제일 헷갈림

가장 헷갈린 부분은 Shift를 누른 상태에서 flip이 발생하는 경우였다.

이 상황에서는 조건이 여러 개 동시에 걸린다.

- 포인터가 위치한 칸은 포함되어야 한다.
- 시작 선택창의 비율은 유지되어야 한다.
- 기준 anchor도 자연스럽게 유지되어야 한다.
- crossing이 발생하면 flip이 토글되어야 한다.
- 결과 width/height는 양수여야 한다.

작업 중에 실제로 헷갈렸던 케이스가 있다.

`startRect: { x: 6, y: 6, width: 5, height: 5 }`

RB 핸들을 잡고 Shift를 누른 상태에서 포인터가 `{ x: 4, y: 5 }`로 간다.

처음에는 이 결과를 잘못 생각했다. 너무 작게 보기도 했고, 너무 크게 보기도 했다. 잠깐은 `4x4`라고 생각했지만, 다시 계산해보니 정답은 `{ x: 4, y: 4, width: 3, height: 3, flipH: true, flipV: true }`였다.

왜냐하면 포인터 `(4, 5)`를 포함해야 하고, 기존 기준점 쪽 칸도 포함해야 하고, 정사각형 비율도 유지해야 하기 때문이다. `(4, 4)`부터 `(6, 6)`까지가 필요한 최소 정사각형이다.

이 케이스는 블로그에 꼭 쓰고 싶다. 사람이 왜 헷갈리는지 잘 보여준다. 코드보다 먼저 기대값을 놓고, 그 기대값이 왜 맞는지 설명하는 과정이 중요했다.

## 구현을 나눈 방식

구현은 대략 이런 식으로 나뉘었다.

먼저 자유 리사이즈를 계산한다.

- 코너 핸들은 반대쪽 꼭짓점을 anchor로 잡는다.
- 엣지 핸들은 반대쪽 변을 고정한다.
- inclusive range로 `x`, `y`, `width`, `height`를 만든다.
- crossing 여부로 flip을 토글한다.

그 다음 필요하면 비율을 맞춘다.

- 엣지 핸들은 중심을 유지하면서 반대 축을 확장한다.
- 코너 핸들은 anchor와 pointer가 만든 사각형을 기준으로 부족한 축을 확장한다.
- 크기 계산은 소수점이 나오면 올림한다. 포인터 칸을 빠뜨리면 안 되기 때문이다.

flip을 막아야 하면 포인터를 먼저 clamp한다. 그러면 crossing 자체가 발생하지 않는다.

## SelectionTool에 다시 연결

순수 함수가 어느 정도 잡힌 뒤 실제 서비스 코드에 연결했다.

기존 `SelectionTool`은 리사이즈 switch 문이 길었다. 핸들별 계산, Shift 분기, flip 정규화, 상태 업데이트가 한곳에 있었다.

이제는 훨씬 단순해졌다.

`SelectionTool`은 포인터를 캔버스 좌표로 바꾼다. 그리고 `resizeSelectionFromHandle`을 호출한다. 결과를 `selection` 상태에 넣고 worker에 전달한다.

즉, `SelectionTool`은 도구 역할만 하고, 리사이즈 수학은 테스트 가능한 함수가 담당한다.

그때 잡은 생각이 anchor와 pointer였다.

코너 핸들을 잡으면 반대쪽 꼭짓점은 anchor가 된다. LT를 잡으면 오른쪽 아래, RB를 잡으면 왼쪽 위가 anchor다. 포인터와 anchor는 결과 사각형 안에 반드시 들어가야 하고, flip이 허용되는 상태에서는 둘이 만든 inclusive rect가 자유 리사이즈의 raw rect가 된다.

이 관점으로 보니 `keepRatio=false`와 `keepRatio=true`가 완전히 다른 문제가 아니었다. 둘 다 먼저 anchor와 pointer로 raw rect를 만든다. free resize는 그 raw rect를 그대로 쓰고, ratio resize는 그 raw rect를 시작 비율에 맞게 확장한다. 이때 부족한 축은 올림으로 키운다. 포인터가 있는 칸을 놓치면 안 되기 때문이다.

이 리팩터링에서 마음에 들었던 점은 특수한 `+1`, `+2` 보정이 줄었다는 것이다. inclusive 좌표계에서 끝 칸을 포함하기 위한 `+1`은 규칙이다. 하지만 기대값 하나를 맞추기 위한 `+2` 같은 보정은 냄새였다. 코드를 보면서 "이 숫자가 좌표계에서 나온 건가, 아니면 테스트 하나를 통과시키려고 붙인 건가"를 계속 확인했다.

## flip된 시작 상태에서 다시 리사이즈하기

초기 `flipH=true`, `flipV=true` 상태가 특히 중요했다.

기본 상태에서 crossing이 발생하면 flip이 켜지는 것은 상대적으로 쉽다. 그런데 이미 뒤집힌 도형에서 다시 crossing이 발생하면 flip이 꺼져야 한다. 그래서 flip은 결과 rect의 방향만 보고 정하는 값이 아니라, 시작 flip 상태에서 crossing 여부를 XOR처럼 적용하는 값이라고 볼 수 있다.

대표 케이스는 이것이었다.

```ts
resizeSelectionFromHandle({
  startRect: { x: 4, y: 3, width: 3, height: 4 },
  handle: "LT",
  pointer: { x: 10, y: 10 },
  keepRatio: false,
  startFlipH: true,
  startFlipV: true,
})
```

기대값은 `{ x: 6, y: 6, width: 5, height: 5, flipH: false, flipV: false }`다. LT를 잡고 오른쪽 아래 anchor를 지나가면 두 축 모두 다시 crossing이 발생한다. 시작 flip이 켜져 있었기 때문에 결과 flip은 꺼진다.

이 케이스는 "flip 상태는 rect의 x/y/width/height와 별개의 상태"라는 점을 잘 보여준다. rect는 항상 정규화된 양수 크기이고, flip은 픽셀 내용을 어느 방향으로 뒤집어 보여줄지에 대한 상태다.

## Shift + 직사각형 + 올림 정책

정사각형보다 직사각형에서 더 많은 실수가 나왔다.

예를 들어 시작 rect가 `{ x: 6, y: 6, width: 4, height: 3 }`이고, LB 핸들을 잡고 Shift를 누른 상태에서 pointer가 `{ x: 11, y: 4 }`로 가는 케이스가 있었다.

한때 기대값을 크게 잡기도 했지만, 최종적으로는 이 값이 맞았다.

```ts
{ x: 9, y: 4, width: 3, height: 3, flipH: true, flipV: true }
```

여기서 중요한 것은 "비율 유지"가 항상 더 크게 확장한다는 뜻이 아니라는 점이다. anchor와 pointer가 만든 raw rect를 기준으로 시작 비율을 만족하는 최소 크기를 찾는다. 부족한 축을 채울 때는 올림을 쓴다. 포인터 칸 포함이 최우선이고, 그 다음이 비율이다.

중간에 "가로 4, 높이 3이었는데 높이가 4가 되어야 한다면 너비는 몇인가" 같은 질문을 던졌다. 정책은 반올림이나 내림이 아니라 올림이었다. 비율을 그대로 유지하려고 계산했을 때 소수점이 나오면, 내림은 포인터 칸을 빠뜨릴 위험이 있다. 그래서 올림이 맞다.

## 단일축 Shift 리사이즈

엣지 핸들에서도 Shift를 누를 수 있다. L/R은 사용자가 가로만 직접 움직이지만, 비율을 유지하려면 세로도 같이 바뀐다. T/B는 반대로 높이를 직접 움직이고 너비가 따라온다.

처음에는 이전 구현처럼 L/R에서 top을 고정하고 높이를 늘리는 방식이 있었다. 그런데 일반적인 그래픽 툴 감각으로 보면 L이나 R을 잡고 Shift를 누르면 세로 중심을 기준으로 비율이 맞춰지는 편이 자연스럽다. 그래서 단일축 Shift 리사이즈를 center 기준으로 바꿨다.

테스트도 이 정책을 문서화했다.

R 핸들에서 시작 rect가 `{ x: 2, y: 2, width: 6, height: 3 }`, pointer가 `{ x: 9, y: 3 }`이면 width는 8이 된다. 시작 비율은 2:1이므로 height는 4가 된다. 기존 height 3에서 4로 늘어났으니 y는 중심을 유지해 그대로 2가 된다.

B 핸들에서는 height가 5가 되고, ratio 때문에 width는 10이 된다. 기존 width 6에서 10으로 늘어났기 때문에 x는 중심을 유지하려고 0으로 이동한다.

```ts
{ x: 0, y: 2, width: 10, height: 5, flipH: false, flipV: false }
```

이 부분은 나중에 블로그에서 "그래픽 툴 감각과 내부 좌표계가 충돌하는 지점"으로 쓰기 좋다.

## ResizeTool에도 같은 계산을 쓰기

처음에는 `SelectionTool`만 `resizeSelectionFromHandle`을 사용했다. 그런데 `src/app/tools/resizeTool.ts`에도 별도의 핸들 리사이즈 switch 문이 남아 있었다.

이건 위험했다. 선택창 리사이즈와 캔버스 리사이즈가 비슷한 수학을 서로 다른 코드로 갖고 있으면, 한쪽에서 고친 inclusive 규칙이나 Shift 정책이 다른 쪽에는 반영되지 않는다.

그래서 `ResizeTool`도 같은 순수 함수를 쓰도록 바꿨다. 다만 캔버스 리사이즈에서는 flip을 허용하면 안 된다. 캔버스 크기를 줄이다가 반대쪽으로 넘어갔다고 캔버스가 뒤집히면 이상하다. 여기서 `allowFlip: false`가 필요해졌다.

`allowFlip=false`의 핵심은 flip 플래그만 false로 만드는 것이 아니다. 그렇게 하면 rect는 이미 반대쪽으로 넘어간 상태인데 표시만 flip이 안 된 이상한 결과가 된다. 올바른 방법은 리사이즈 계산 전에 pointer를 anchor까지만 clamp해서 crossing 자체를 막는 것이다.

예를 들어 RB 핸들에서 시작 rect가 `{ x: 6, y: 6, width: 5, height: 5 }`이고 pointer가 `{ x: 3, y: 3 }`으로 넘어가도, `allowFlip=false`라면 결과는 `{ x: 6, y: 6, width: 1, height: 1, flipH: false, flipV: false }`여야 한다.

이 케이스를 테스트로 추가했다. `allowFlip=false`는 옵션이지만, 옵션의 의미가 코드에만 있으면 나중에 잊기 쉽다. 테스트가 문서 역할을 한다.

## maxSize clamp와 고정 변

`ResizeTool`에서 `resizeSelectionFromHandle` 결과를 그대로 쓰면 대부분 맞지만, maxSize clamp가 끼어들면 L/T 계열에서 조심해야 한다.

예를 들어 L 핸들을 잡고 왼쪽으로 크게 늘렸는데 width가 `paintConfig.maxSize`로 잘리면, x도 그 잘린 width에 맞게 다시 계산해야 한다. 그래야 오른쪽 고정 변이 유지된다.

그래서 `resizeTool.ts`에서는 순수 함수 결과의 width/height를 clamp한 뒤, L 계열이면 `x = start.x + start.w - width`, T 계열이면 `y = start.y + start.h - height`로 다시 맞춘다.

이건 순수 함수의 책임이 아니다. 순수 함수는 주어진 포인터와 정책으로 이상적인 rect를 계산한다. `paintConfig.maxSize` 같은 앱 제한은 도구 레이어의 책임이다.

## WebGL core와 시각적 불일치

가장 마지막에 중요한 문제가 나왔다.

단일축 Shift를 center 기준으로 바꾸자 선택창 상태에서는 x/y가 바뀌었다. 하지만 WebGL core 쪽에서는 여전히 top이 anchor라고 가정하는 듯한 시각적 불일치가 생겼다.

처음에는 단일축 Shift 정책을 다시 top/left 고정으로 돌려야 하나 생각했다. 실제로 잠깐 그렇게 판단했다. 하지만 다시 보니 문제는 정책이 아니라 core에 변경된 x/y가 제대로 전달되지 않는 쪽이었다.

`ResizeTool.up()`에서는 이미 `changeCanvasSize(x, y, selection.width, selection.height)`로 selection의 x/y를 넘기고 있었다. 그런데 core 입구인 `WebGL2Controller.resizeLayer()`에서 y를 변환하는 코드가 이상했다.

기존 코드는 대략 이런 의미였다.

```ts
if (py !== 0) {
  newY = 0;
} else {
  newY = py + diffH;
}
```

즉 app 쪽에서 y가 0이 아니면 WebGL 쪽 y를 무조건 0으로 덮어버렸다. 그래서 center 기준으로 y가 바뀌어도 core는 그 y를 반영하지 못했다.

수정은 이랬다.

```ts
const newY = paintOptions.height - height - py;
paint.resizeLayer(px, newY, width, height);
```

app 좌표계는 top-left 기준이고, WebGL은 bottom-left 기준이다. 새 캔버스 안에서 기존 이미지를 어디서부터 샘플링할지를 WebGL 좌표로 바꿔야 한다. 그래서 `oldHeight - newHeight - py` 형태가 된다.

이 수정 후에는 단일축 Shift의 center 기준 x/y가 core resize에도 반영된다. 즉 UI selection rect와 실제 WebGL resize 결과가 같은 rect를 바라보게 된다.

## 오늘 작업에서 남긴 교훈

첫째, 기대값이 맞는지 먼저 확정해야 한다. 테스트가 틀린 상태에서 구현을 고치면, 코드는 점점 이상한 특수 케이스를 품게 된다.

둘째, "포인터와 anchor가 결과 사각형 안에 있어야 한다"는 식의 기하 규칙은 특수 케이스보다 강하다. 숫자 보정을 덧붙이기 전에 이런 규칙으로 설명되는지 봐야 한다.

셋째, 순수 함수로 분리해도 실제 앱에 다시 연결할 때 좌표계 변환 문제가 남는다. app은 top-left, WebGL은 bottom-left다. selection 상태가 맞아도 core 변환이 틀리면 사용자는 버그로 본다.

넷째, 옵션은 플래그만 바꾸는 것이 아니라 동작의 원인을 바꿔야 할 때가 있다. `allowFlip=false`는 flip 결과를 억지로 false로 만드는 옵션이 아니라, crossing이 일어나지 않게 pointer를 clamp하는 옵션이었다.

다섯째, 같은 리사이즈 수학은 한 곳에 있어야 한다. `SelectionTool`과 `ResizeTool`에 비슷한 switch 문이 따로 있으면 언젠가 반드시 정책이 갈라진다.
