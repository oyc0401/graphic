좋습니다. 말씀해주신 배경과 목표, 현재 구조를 바탕으로 WebGL2 기반 그래픽 에디터의 구조 개선과 아키텍처 리스크를 깊이 있게 리뷰하고, 향후 수십만~백만 MAU를 감당할 수 있는 구조로 나아가기 위한 전략을 모두 정리하겠습니다. 여기에 포함될 내용은 다음과 같습니다:

- 전체 코드 구조 및 레이어별 책임 분리 리뷰
- WebGL2 렌더링 파이프라인과 selection/brush/liquify 등 도구 관리 구조 리뷰
- 워커 기반 구조의 장단점 분석과 병렬성 확장 가능성
- 히스토리 시스템 구현을 위한 기반 구조 리뷰 및 제안 (reversible dataflow, selection 포함)
- 앞으로 구현하실 floodfill, 레이어, 저장 구조에 대한 구조적 방향 제안
- SEO, i18n, SSR을 위한 구조 전환 고려사항
- 코드 구조 리스크와 필요한 리팩토링 포인트 (현재 상태로 쭉 가도 괜찮을지, 엎을 이유가 있는지)

이 모든 내용을 아키텍처 가이드 문서 형태로 정리해서 드릴게요. 잠시만 기다려주세요.

# WebGL2 기반 픽셀 그래픽 에디터 코드 구조 리뷰

## 서론 (Introduction)
현재 사용자가 개발한 WebGL2 기반 픽셀 그래픽 에디터의 코드를 검토한 결과, 기본적인 동작은 구현되어 있으나 **확장성과 유지보수 측면에서 개선이 필요한 부분**들이 보입니다. 특히 월간 활성 사용자(MAU) 100만 명 이상 규모로 성장함을 고려하면, 현 구조로는 추후 기능 추가와 성능 유지에 어려움이 있을 수 있습니다. 본 문서에서는 전체 코드 구조와 모듈 분리, 개별 툴(브러시, 지우개, 액체변형(liquify), 선택 등) 및 렌더링 매니저, WebGL2 기반 렌더링 기법, 워커/히스토리 구조, 향후 기능(플러드 필, 레이어, DB 연동, 국제화(i18n), SEO/SSR) 등을 **시스템 아키텍처 관점**에서 리뷰하고 개선 방향을 제시합니다. 아래 내용은 숙련된 시스템 설계자가 코드리뷰를 진행하며 후배 개발자에게 해주는 제언 형식으로 작성되었습니다.

## 전체 코드 구조 및 모듈 책임 분리
현재 코드의 전반적인 구조를 살펴보면 **모듈 간 책임 분리**가 완벽히 이루어지지 않은 것으로 추정됩니다. 이는 초기 프로토타입 단계에서는 동작 구현에 초점을 맞추었기 때문일 수 있으나, 기능이 늘어나고 사용자 규모가 커질수록 유지보수를 어렵게 만드는 요인입니다. 

- **단일 모듈에 과도한 기능 집중**: 코드 일부에 UI 이벤트 처리, WebGL 렌더링, 도구 로직 등이 한 곳에 섞여 있을 가능성이 있습니다. 이렇게 되면 코드 가독성이 떨어지고 수정 시 의도치 않은 부작용이 발생하기 쉽습니다. 모듈별로 **단일 책임 원칙(SRP)**을 적용해 **UI/이벤트 처리**, **렌더링**, **도구 로직**, **데이터 상태 관리** 등을 분리하는 것이 바람직합니다.
- **전역 상태 관리 문제**: 만약 전역 객체나 변수에 편의상 여러 상태(현재 툴, 선택 영역, 히스토리 스택 등)를 담고 있다면, 이는 모듈 분리를 어렵게 하고 협업 시 충돌을 야기할 수 있습니다. 향후 기능 확장을 염두에 두면, **중앙 상태 관리(예: Redux와 같은 패턴 또는 자체 State Manager)**를 도입하거나, 에디터 핵심 객체(`EditorCore` 등)에 상태를 모아서 관리하도록 구조화하는 것이 좋습니다.
- **파일 및 클래스 구조**: 코드베이스가 커지면 파일 단위로도 구조를 정리해야 합니다. 현재 **바닐라 JS**로 작성되었다고 하니 ES6 모듈 또는 TypeScript 클래스로의 리팩토링을 고려해볼 수 있습니다. 예를 들어 `CanvasRenderer.js`, `ToolBrush.js`, `ToolEraser.js`, `HistoryManager.js`, `LayerManager.js` 등의 파일로 나누고, 각각 명확한 인터페이스를 가지도록 합니다. 이렇게 하면 새로운 팀원이 합류하거나 기능 추가 시 해당 모듈만 이해하면 되므로 유지보수성이 높아집니다.
- **디자인 패턴 적용**: 복잡한 Undo/Redo(히스토리)나 명령 처리에는 **커맨드 패턴(Command Pattern)** 등의 설계 패턴을 적용하는 것이 권장됩니다 ([javascript - How to make a undo/redo function - Stack Overflow](https://stackoverflow.com/questions/54416318/how-to-make-a-undo-redo-function#:~:text=While%20there%27s%20many%20different%20ways,Pattern%20and%20the%20Command%20Pattern)). 예를 들어, 모든 편집 작업을 `Command` 객체로 추상화하고, `execute()`와 `undo()` 메서드를 갖게 하는 구조입니다. 이때 편집 대상 상태(예: 캔버스 픽셀 데이터)를 변경하는 로직은 Command의 `execute`에, 복구 로직은 `undo`에 구현합니다. 이러한 패턴을 도입하면 기능 확장(새로운 툴 추가 등)시 새로운 커맨드 클래스를 추가하는 것으로 Undo/Redo까지 일관되게 동작하게 할 수 있습니다.

**요약**: 전체적으로 **MVC 혹은 MVVM**에 준하는 아키텍처로 개편하는 것을 권장합니다. 뷰/UI는 캔버스와 툴 패널 등에 대한 표시 및 이벤트 처리만 맡기고, 에디터의 상태와 로직은 별도의 모델/뷰모델이 담당하도록 하면 모듈 경계가 명확해집니다. 또한 초기 코드가 프로토타입 수준이라면, MAU 증가 전에 핵심 구조를 한 차례 리팩토링하여 **기능별 모듈 분리**를 완료하는 것이 이후 개발 속도를 높이고 리스크를 줄이는 데 도움이 될 것입니다.

## 툴 구조 (브러시/지우개/액체변형/선택 등)와 렌더링 매니저 설계
픽셀 편집기에는 다양한 **도구(Tool)**가 존재하며, 이들의 동작은 각기 다르지만 공통된 인터페이스를 가질 수 있습니다. 현재 구현된 브러시, 지우개, 액체변형(Liquify), 선택 도구 각각의 코드 구조와 **렌더링 매니저(Rendering Manager)**의 상호작용을 평가하면 다음과 같습니다:

- **툴 인터페이스의 일관성**: 이상적인 구조에서는 각 툴이 공통 인터페이스(예: `onPointerDown`, `onPointerMove`, `onPointerUp`, `apply()` 등을 가진 클래스)로 구현되어, 에디터는 현재 활성 툴의 해당 메서드를 호출하는 방식입니다. 이렇게 하면 새로운 툴 추가도 수월해집니다. 현 코드에서 만약 툴별 구현이 일관되지 않고, 어떤 것은 이벤트 리스너 내부에 직접 로직을 가지고 있다거나, 조건문으로 툴 종류를 분기하고 있다면 개선이 필요합니다. **예시**: `ToolBase`라는 추상 클래스를 만들고, 브러시(`BrushTool`), 지우개(`EraserTool`), 변형(`LiquifyTool`), 선택(`SelectTool`) 등이 이를 상속하여 구현하도록 리팩토링하면 구조가 정돈됩니다.
- **렌더링 매니저의 역할**: **Rendering Manager**는 캔버스(WebGL 컨텍스트)에 그려지는 모든 작업을 통합 관리하는 모듈입니다. 올바른 설계라면 **툴은 그려야 할 내용 또는 좌표를 계산**만 하고, **실제 화면 업데이트는 렌더링 매니저가 담당**합니다. 이렇게 하면 렌더링 파이프라인을 일원화하여 성능 최적화나 WebGL 상태 관리를 중앙에서 제어할 수 있습니다. 현재 구조에서 각 툴이 직접 WebGL API 호출을 한다면, 렌더링 매니저의 역할이 분산되어 있는 것입니다. 이 경우 **렌더링 경로를 단일화**하도록 구조 개선을 권장합니다. 예를 들어, 브러시 툴은 "이 위치에 이 크기의 브러시 자국을 그려달라"는 명령/데이터만 렌더러에 전달하고, 렌더러는 해당 명령을 처리해 캔버스 텍스처에 반영하도록 합니다.
- **브러시/지우개 구현**: 브러시는 색상을 찍는, 지우개는 투명하게 만드는 도구로 구현은 유사합니다. WebGL2를 사용한 현재 구현이 만약 **텍스처에 직접 픽셀을 찍는 방식**이라면, 성능을 위해 한 번의 드로우 콜로 여러 픽셀을 찍거나 브러시 텍스처(스탬프)를 활용하는 방안을 고려해야 합니다. 예를 들어, 브러시 모양(원형 등)을 텍스처로 만들어 해당 텍스처를 현재 캔버스 텍스처 위에 **블렌딩**하는 셰이더를 사용하면, 매우 빠르게 브러시 도장을 찍을 수 있습니다. 지우개는 동일한 방법으로 투명색(또는 알파 0)을 브러시 모양으로 블렌딩하면 구현됩니다. 현재 구조에서 이러한 최적화가 부족하다면, **브러시/지우개 전용 셰이더와 텍스처**를 도입하는 개선이 가능합니다.
- **액체변형(Liquify) 구현**: Liquify는 영역을 부드럽게 밀어내거나 당기는 효과로, CPU로 처리하면 매우 느린 작업입니다. WebGL2를 도입한 것은 이를 **GPU 셰이더로 실시간 처리**하기 위함으로 보입니다. 현 구조에서 Liquify 툴이 별도의 Framebuffer나 셰이더 패스를 사용한다면 적절합니다. 만약 CPU에서 픽셀을 조작하고 다시 텍스처에 업로드하는 방식이라면, 대용량 이미지에서 성능 문제가 발생할 수 있습니다. 권장 방식은 Liquify 툴이 **변형 벡터 필드**를 생성하고, 렌더링 매니저가 해당 벡터 필드를 적용해 텍스처를 샘플링 변형하는 셰이더(예: displacement map)를 돌리는 것입니다. 이렇게 하면 실시간 미리보기도 가능하고 GPU 가속의 이점을 살릴 수 있습니다. 향후 이 구조는 다른 효과(예: 회전 변형, 페르소나 효과 등)에도 응용될 수 있어 확장성이 높습니다.
- **선택(Selection) 도구 구현**: 선택 도구는 보통 사각형 영역 선택, 올가미(Lasso), 색상으로 선택 등 다양한 모드가 있습니다. 현재는 기본적인 드래그 박스(selection box) 또는 픽셀 단위 마스크로 구현되었을 텐데, 이 **선택 상태를 어떻게 유지하고 표시하느냐**가 중요합니다. 
  - 선택 영역 데이터는 **별도의 비트마스크 또는 텍스처**로 유지하는 것이 일반적입니다. 선택된 부분=1, 나머지=0 형태의 2D 배열 또는 알파 텍스처를 유지하면, 나중에 필터나 브러시 적용 시 이 마스크를 사용하여 적용 범위를 제한할 수 있습니다. WebGL2를 사용하고 있으므로, 이 선택 마스크를 텍스처로 GPU에 유지하면 좋습니다.
  - 선택 영역의 **시각적 표시**(예: 테두리에 애니메이션 "개미행렬" 표시, 혹은 선택 영역 내부/외부 반투명 처리)는 렌더링 매니저에서 추가 **오버레이 패스**로 처리하는 것이 효율적입니다. Photopea와 같은 사례에서도 “selection area highlighting”을 GPU로 처리하고 있는데, Photopea는 *“각 레이어의 픽셀 데이터를 WebGL 메모리에 저장하고, WebGL을 블렌딩과 UI(줌, 배경그리드, 선택영역 하이라이트 등)에 활용”*하고 있습니다 ([  Photopea 1.3](https://blog.photopea.com/photopea-1-3.html#:~:text=Pixel%20data%20of%20each%20layer,use%20hadrware%20acceleration%20also%20for)). 즉, 선택 영역 표시를 위해 따로 CPU에서 캔버스를 덧그리는 것이 아니라 GPU에서 해당 영역에 하이라이트 처리를 해주고 있다는 의미입니다. 현재 구조도 만약 선택 표시를 Canvas 2D나 DOM 요소로 하고 있다면, 향후 복잡한 선택 형태에서도 성능과 일관성을 유지하도록 **WebGL 기반 오버레이**로 통합하는 것을 고려해야 합니다.
  - **선택 툴과 다른 툴의 연계**: 구조적으로 선택 도구가 활성화될 때는 브러시 등 다른 편집 툴이 선택 영역 내에서만 동작하거나(보통 selection mask에 의해 보호), 혹은 선택 밖은 편집이 막히게 해야 합니다. 이를 위해 **툴 로직**에서 항상 현재 selection 마스크를 참고하거나, 렌더링 단계에서 selection 마스크를 적용하여 선택 외 지역엔 변화가 없도록 처리해야 합니다. 현 코드에서 이러한 연계가 간소화되어 있다면, Selection 모듈을 central state로 승격시켜 다른 모듈이 쉽게 확인할 수 있게 개선할 필요가 있습니다.

**렌더링 매니저 종합 평가**: 렌더링 매니저가 **모든 그리기 업데이트를 단일 루프로 관리**하고 있다면, 예를 들어 `render()` 함수에서 현재 화면에 그려야 할 모든 요소(레이어, 현재 작업 중인 툴의 미리보기, 선택 영역 등)를 그린다면 이상적입니다. 그러나 만약 개별 툴이 `requestAnimationFrame` 등을 각각 돌리거나, 렌더링 시점을 제각기 정한다면, **렌더링 타이밍을 통합**해야 합니다. 또한 **오프스크린 버퍼 활용**도 고려하세요. 예를 들어, 액체변형 툴의 미리보기는 별도 오프스크린에 그리고, 완승(confirm) 시 메인 캔버스에 적용하는 식으로 하면 복잡한 효과도 편집 중에 ON/OFF가 수월합니다.

결론적으로, **각 툴은 독립된 모듈로 구현**하되 **렌더링은 중앙의 Renderer가 통제**하는 구조가 가장 유지보수에 유리합니다. 이렇게 하면 새로운 툴을 추가해도 기존 렌더링 파이프라인에 쉽게 녹일 수 있고, 툴 간 공통 기능(예: 그리기 한계, 선택 마스크 적용 등)도 Renderer에서 일괄 처리 가능하여 코드 중복이 줄어듭니다.

## WebGL2 기반 렌더링 구조의 확장성과 성능 평가
WebGL2를 활용한 현재 렌더링 구조를 확장성과 성능 측면에서 살펴보면, **GPU의 장점을 살리면서도 한계를 인지**하는 전략이 필요합니다. MAU 100만 사용자를 기대한다면, 사용자 환경도 다양할 것이므로 **성능과 호환성**을 모두 고려해야 합니다.

- **WebGL2 활용 장점**: WebGL2는 2D 캔VAS에 비해 대용량 픽셀 데이터 처리와 실시간 효과 적용에 강점이 있습니다. 이미 GPU를 사용함으로써 브라우저 메인 스레드 부담을 낮추고 고해상도 편집에 대비한 점은 좋습니다. 실제로 Photopea 같은 대형 웹 편집기도 GPU 가속을 통해 여러 레이어 블렌딩을 CPU 대비 10배 이상 가속했습니다 ([  Photopea 1.3](https://blog.photopea.com/photopea-1-3.html#:~:text=Pixel%20data%20of%20each%20layer,other%20operations%20in%20the%20future)). 현재 구조에서도 WebGL2의 **텍스처, Framebuffer, 셰이더** 등을 잘 활용하고 있다면, 향후 레이어나 필터 추가 시 비교적 수월할 것입니다.
- **GPU 메모리 관리**: 한편 GPU에 모든 이미지를 올려놓고 작업하면 **메모리 한계**를 맞닥뜨릴 수 있습니다. 대부분의 GPU는 최대 텍스처 크기 제한(예: 16384x16384px 정도)이 있고 ([r/photopea on Reddit: WebGL is not being used when I choose the ...](https://www.reddit.com/r/photopea/comments/1arslee/webgl_is_not_being_used_when_i_choose_the_use/#:~:text=,to%2016384%20x%2016384%20pixels)), 메모리가 한정적입니다. Photopea도 이미지가 너무 큰 경우 WebGL을 비활성화하고 CPU로 처리하는 fallback이 있습니다 ([r/photopea on Reddit: WebGL is not being used when I choose the ...](https://www.reddit.com/r/photopea/comments/1arslee/webgl_is_not_being_used_when_i_choose_the_use/#:~:text=,to%2016384%20x%2016384%20pixels)). 따라서 **대용량 이미지에 대한 예외 처리** 또는 **텍스처 타일링** 전략이 필요합니다. 예를 들어, 현구조에서 한 캔버스 텍스처에 전부 올리는 방식이라면, 차후 **이미지를 타일 단위로 분할해 여러 텍스처로 관리**하는 기능을 염두에 두어야 합니다. (초기에 구현하지 않더라도 구조적으로 확장이 가능해야 합니다.)
- **확장성**: WebGL로 구현된 현재 도구들은 주로 픽셀 조작용 셰이더일 텐데, **새로운 셰이더 효과 추가**가 얼마나 쉬운 구조인지 평가해야 합니다. 만약 셰이더 소스코드가 여기저기 흩어져 있고 WebGL 초기화가 분산되어 있다면, 이를 정리해야 합니다. **Shader 관리 모듈**을 만들어 셰이더 소스들을 모아 관리하고, 컴파일/링크를 일괄 수행, 필요한 유니폼 변수를 업데이트하는 헬퍼를 두면 새로운 셰이더(예: 블렌딩 모드 추가 구현 등) 작성이 쉬워집니다. 
- **퍼포먼스 모범 사례**: WebGL 관련 성능 최적화 모범 사례를 현재 구조에 적용했는지 검토합니다 ([WebGL best practices - Web APIs - MDN Web Docs - Mozilla](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#:~:text=WebGL%20best%20practices%20,don%27ts%2C%20but%20also%20details%20why)) ([WebGL2 Picking](https://webgl2fundamentals.org/webgl/lessons/webgl-picking.html#:~:text=WebGL2%20Picking%20WebGL%20itself%20is,of%20objects%20to%20be%20selected)). 예를 들면:
  - 가능한 **정점 배치 최소화** (2D 이미지의 경우 전체 화면 그리기에 두 개 삼각형 정점이면 충분).
  - **텍스처 접근 최적화**: 셰이더에서 텍스처 fetch를 최소화하고 메모리 공동사용(locality)을 높이는 방식.
  - **不要한 readback 지양**: CPU<->GPU 간 데이터 복사는 매우 비싸므로, `gl.readPixels` 등을 남용하지 않는지 확인해야 합니다. 종종 개발 중 디버깅이나 간단한 구현을 위해 `readPixels`로 픽셀 데이터를 가져와 처리하는 경우가 있는데, 1M 사용자가 쓰는 서비스에선 병목이 됩니다. 만약 selection 구현이나 flood fill 등을 위해 CPU로 데이터를 가져오는 부분이 있다면, 이를 **GPU 상에서 해결**하거나 **비동기 워커**로 돌리는 방향으로 바꿔야 합니다.
  - **상태 변경 최소화**: WebGL 상태(state)나 셰이더 프로그램 바꾸기는 비용이 크므로, 렌더링 매니저가 **드로우 호출을 정렬/병합**해서 수행하는 것이 좋습니다. 예컨대 여러 레이어를 그릴 때 각기 프로그램을 바꾸는 것보다, 가능한 한 프로그램 하나로 처리가 끝나도록 한다든지, 아니면 미리 FBO에 그려놓고 한 번에 합성한다든지의 전략이 필요합니다.
- **모바일/호환성**: 100만 명 규모라면 저사양 PC나 모바일 브라우저에서도 동작해야 합니다. WebGL2 지원이 완벽하지 않은 환경(특히 일부 구형 iOS 기기)은 WebGL1로 fallback이 필요할 수 있습니다. 현재 코드가 WebGL2 전용이라면, **호환 레이어**를 마련해 두는 것도 고민해야 합니다. 예를 들어, WebGL2에서만 되는 기능(테xture format 등)을 사용했다면 WebGL1에서의 대체 경로를 준비하거나, 최소한 지원 여부를 체크해 **지원 안 되는 경우 경고 및 사용 제한**을 안내하는 것도 사용자 경험 측면에서 필요합니다.
- **멀티캔버스 구조**: 확장성을 위해서는 **멀티 캔버스 (멀티 레이어) 구조**를 고려해야 합니다. 각 레이어를 별도 텍스처로 가지려면, WebGL 하나의 컨텍스트에 다수 텍스처를 관리하거나, 아니면 레이어별로 OffscreenCanvas/별도 WebGL 컨텍스트를 둘 수도 있습니다. 둘 다 장단이 있는데, 일반적으로 하나의 컨텍스트에서 여러 텍스처를 갖는 쪽이 컨텍스트 전환 비용이 없어서 유리합니다. 이러한 **다층 구조**를 구현하려면 현 코드에서 캔버스/텍스처를 다루는 방식을 일반화해둘 필요가 있습니다. 즉, "현재 활성 레이어" 개념을 두고, 도구 입력이 항상 이 활성 레이어의 텍스처에 작용하도록 만드는 것입니다. 현재 싱글 레이어로 짰다면, 이 부분을 추상화하는 리팩토링이 추후 필요합니다.

**요약**: WebGL2 기반 구조는 성능 측면에서 올바른 방향이지만, **대용량 처리에 대한 대비, 셰이더/텍스처 관리의 체계화, GPU-CPU 간 병목 최소화**가 과제로 보입니다. 또한 다양한 환경에 대한 graceful degradation(점진적 기능 저하) 또는 fallback도 고려해야 1백만 사용자 수준의 제품으로서 안정성을 담보할 수 있습니다.

## 워커 구조 분리 및 히스토리 연동
**Web Workers**의 적절한 활용은 대규모 웹 애플리케이션에서 메인 스레드의 부하를 줄이는 핵심 기법입니다. 이미지 편집기에서도 **무거운 연산**(예: 큰 영역 칠하기, 복잡한 필터 적용 등)은 워커로 분리하는 것이 좋습니다. 현재 코드에서 워커 사용 여부와 구조를 검토한 결과와, 히스토리(Undo/Redo) 기능과의 연계를 고려한 평가는 다음과 같습니다:

- **워커로 분리하기 적합한 작업**: 대표적으로 **Flood Fill(채우기)**, **대용량 필터(예: 블러)**, **이미지 불러오기/저장 등 I/O**, **히스토리 상태 저장(스냅샷 생성)** 등이 있습니다. 이러한 작업은 메인 스레드에서 수행하면 UI가 멈추거나 프레임 드랍을 유발할 수 있으므로, 워커(thread)로 보내 비동기로 처리하는 것이 바람직합니다. **현재 구조**에서 만약 모든 작업이 메인에서 일어난다면, 우선 사용자의 체감 성능 향상을 위해 **핵심 연산의 워커 오프로딩(Offloading)**을 계획해야 합니다. 
- **워커 통신 및 데이터 복사**: 워커로 이미지를 처리하려면 픽셀 데이터를 보내야 하는데, 데이터 양이 많아 **복사 비용**이 문제됩니다. HTML5의 `postMessage`는 기본적으로 데이터를 복사하지만, **Transferable 객체**(ArrayBuffer 등)을 사용하면 복사 없이 소유권 이동이 가능합니다. 특히 **OffscreenCanvas**는 transfer가 가능한 객체여서, 메인 스레드 캔버스를 워커로 넘겨줄 수 있습니다 ([OffscreenCanvas—speed up your canvas operations with a web worker  |  Articles  |  web.dev](https://web.dev/articles/offscreen-canvas#:~:text=Moving%20heavy%20calculation%20to%20a,on%20the%20source%20canvas%20automatically)). 이 API를 활용하면 **렌더링 자체를 워커에서 수행**하게 할 수도 있습니다. 예를 들어:
  - 메인 스레드: `const offscreen = canvas.transferControlToOffscreen(); worker.postMessage({canvas: offscreen}, [offscreen]);`
  - 워커 스레드: 오프스크린 캔버스로 WebGL 컨텍스트 생성 후 렌더링 루프 수행.

  이 방식으로 구현하면, 주 쓰레드에서는 UI 이벤트만 처리하고 모든 그리기는 워커가 담당하여 **메인 UI가 블록될 일이 없게**됩니다 ([OffscreenCanvas—speed up your canvas operations with a web worker  |  Articles  |  web.dev](https://web.dev/articles/offscreen-canvas#:~:text=Unblock%20main%20thread)). 다만 구현 복잡도가 증가하고, 디버깅이 어려워질 수 있으므로 단계적으로 도입하는 것이 좋습니다. 우선 간단히는, **워커를 이용해 연산만 분리**하고 렌더링은 아직 메인에서 하는 방식으로도 충분한 개선을 얻을 수 있습니다. (예: flood fill로 채울 픽셀 목록을 워커에서 계산해 보내면, 메인에서 그 결과만 적용)
- **히스토리(Undo/Redo)와 워커 연계**: 워커에서 수행된 작업도 히스토리로 남겨야 합니다. 이때 구조적으로 고려해야 할 점은 **비동기 작업의 완료 시점**에 히스토리 상태를 기록하는 것입니다. 예를 들어, Flood Fill을 워커에서 수행하도록 하면, 워커가 작업 완료 메시지를 보낼 때까지 메인에서는 해당 작업이 끝난 것을 모릅니다. 따라서 **히스토리 관리자는 비동기 작업을 지원**해야 합니다. 구현상 방법은:
  - **커맨드 패턴 활용**: 워커에 수행시킨 작업도 하나의 `Command`로 간주합니다. `execute()` 호출 시 워커에 메시지를 보내고, 완료 응답이 오면 그 때 히스토리에 push합니다. `undo()` 시에는 해당 영역의 이전 픽셀 데이터를 갖고 있다가 복원하거나, 아니면 Undo용 별도 워커 연산을 또 정의합니다.
  - **Memento 패턴 활용**: 작업 전후의 전체 상태 스냅샷을 저장한다면(물론 비효율적일 수 있지만), 워커에서 작업한 뒤 메인에서 canvas 상태를 받아 바로 스냅샷을 찍어 히스토리에 넣는 방식입니다.

  중요한 것은, **현재 구조에서 워커 결과를 히스토리에 넣을 수 있는 지점이 명확한지**입니다. 만약 현 구조에서 히스토리를 고려하지 않고 워커를 별도로 돌린다면, Undo/Redo 시 워커 작업의 결과를 제대로 취소하거나 되돌리는 데 문제가 생길 수 있습니다. 따라서 **히스토리 관리 모듈**을 만들고, 워커와 메인 양쪽에서 이를 활용하도록 프로토콜을 정하는 것이 좋습니다. 예를 들어, 워커 메시지에 `historyId`를 포함시켜 이 작업이 완료되면 historyId에 해당하는 state를 스냅샷 찍는다든지 하는 협의입니다.
- **현재 워커 분리도 평가**: 만약 현재 코드에 일부 워커 사용이 보인다면, 그 **범위와 분리도**를 살펴봐야 합니다. 예를 들어 렌더링과 별개로 이미지 가져오기/내보내기를 워커로 해두었다면 좋습니다. 또는 Liquify 계산 등을 워커로 했을 수도 있습니다. 그러나 모든 워커는 **메인과 독립적이어야 하며, DOM 접근을 하지 않아야** 합니다. WebGL의 경우 과거에는 워커 내에서 직접 사용할 수 없었지만 OffscreenCanvas 도입으로 가능해졌습니다. **웹.worker 코드**와 **메인 코드**가 적절히 역할을 나누고 있는지 (예: 메인은 UI업데이트/커맨드 발행, 워커는 연산 처리) 확인하고, 아니라면 그렇게 개선합니다.
- **UI 반응성 확보**: 워커 도입의 주요 목적은 **UI 스레드의 작업량 감소**입니다. 히스토리 연동도 중요하지만, 우선 사용자가 **페인트 중에도 인터랙션이 부드러운지**가 핵심입니다. 그러므로 브러시로 그릴 때도 대형 브러시의 경우 워커가 그려줄 수 있다면 더욱 좋겠지만, 브러시는 실시간 반응이 중요해 메인에서 GPU처리하되, **상대적으로 지연을 허용할 수 있는 작업들** (예: 이미지 효과 필터, 자동 보정 등)은 워커로 빼도록 구조를 계획해야 합니다. 
- **동시 작업 이슈**: 여러 워커를 활용하거나 워커 작업 중 사용자가 다른 조작을 할 수 있는 경우, **작업 큐 관리**가 필요합니다. 예컨대 사용자가 아주 큰 영역을 채우기(워커) 실행한 직후 다른 도구로 그리기를 시작했다면, 전후 관계나 히스토리 순서가 꼬일 수 있습니다. 이를 막기 위해 워커 작업이 진행 중일 때는 편집 툴 입력을 잠시 막거나(진행중 표시), 혹은 여러 작업을 병렬로 처리해도 일관성을 해칠 위험이 없도록 해야 합니다. 이 부분은 **UX 정책**과도 연관되지만, 기술적으로 **atomic한 작업 단위**를 어떻게 정의하고 관리할지 구조상 고민해야 합니다.

**요약**: WebWorker를 적극 활용함으로써 **메인 스레드의 부담을 줄이고**, 특히 **비동기 작업에도 히스토리 추적을 일관되게 적용**할 수 있는 구조로 개선해야 합니다. 현재 바닐라 JS 구조에서 이를 도입하려면 코드 조직과 통신 패턴을 정비해야 하므로, 히스토리 기능 구현을 시작하기 전에 워커와 메인 간 메시지 설계, 히스토리 모듈의 비동기 지원 등을 먼저 설계하는 것을 권장합니다. 결과적으로, 잘 구성된 워커 구조는 **UI 반응성 개선과 멀티코어 활용**이라는 두 마리 토끼를 잡을 수 있게 해 줄 것입니다 ([OffscreenCanvas—speed up your canvas operations with a web worker  |  Articles  |  web.dev](https://web.dev/articles/offscreen-canvas#:~:text=Unblock%20main%20thread)).

## 히스토리(Undo/Redo) 기능 설계와 Selection 포함 여부
향후 구현 예정인 **히스토리(Undo/Redo)** 기능을 고려하여, 현재 구조가 이를 얼마나 수용할 수 있는지 평가하고 바람직한 설계를 제안합니다. 특히 **선택 영역(selection)의 히스토리 포함 여부**에 대한 고려가 중요합니다.

- **히스토리 기본 전략**: Undo/Redo 구현에는 크게 두 가지 전략이 있습니다 – **Memento(메멘토) 패턴**과 **Command(커맨드) 패턴** ([javascript - How to make a undo/redo function - Stack Overflow](https://stackoverflow.com/questions/54416318/how-to-make-a-undo-redo-function#:~:text=While%20there%27s%20many%20different%20ways,Pattern%20and%20the%20Command%20Pattern)) ([javascript - How to make a undo/redo function - Stack Overflow](https://stackoverflow.com/questions/54416318/how-to-make-a-undo-redo-function#:~:text=,lead%20to%20the%20new%20state)). 메멘토는 변경 전후 **상태를 통째로 저장**하는 방식이고, 커맨드는 **변경 자체를 기록**하여 실행/역실행 가능한 형태로 남기는 방식입니다. 픽셀 편집기의 경우 이미지 데이터가 커서 메멘토(즉, 전체 캔버스 상태 스냅샷 저장)는 **메모리 오버헤드**가 큽니다 ([javascript - How to make a undo/redo function - Stack Overflow](https://stackoverflow.com/questions/54416318/how-to-make-a-undo-redo-function#:~:text=,any%20state%20change%20is%20captured)). 대신 **커맨드 패턴**을 활용하면 변경된 부분만 저장하거나 역연산을 통해 undo 할 수 있어 효율적입니다 ([javascript - How to make a undo/redo function - Stack Overflow](https://stackoverflow.com/questions/54416318/how-to-make-a-undo-redo-function#:~:text=Each%20action%20is%20coded%20as,a%20Command%20with%202%20methods)). 예를 들어, 브러시로 그린 동작은 “이 위치들에 이 색을 그렸다”라는 커맨드로 기록하고 undo 시 “그 위치들의 이전 색으로 복원”하는 식입니다. 현재 구조에서 이러한 커맨드/히스토리 체계가 자명하게 보이지 않는다면, 아키텍처 차원에서 우선 이 **Command 객체와 History 스택 관리** 클래스를 도입할 필요가 있습니다.
- **Selection 변경의 히스토리 포함**: 전문 그래픽 툴(예: Photoshop)에서는 **선택 영역의 변동도 Undo 히스토리에 포함**됩니다. 사용자가 실수로 선택을 해제했을 때 Undo하면 다시 선택이 복구되는 것이 자연스럽기 때문입니다 ([Adobe software undo selection - Graphic Design Stack Exchange](https://graphicdesign.stackexchange.com/questions/77286/adobe-software-undo-selection#:~:text=I%20do%20not%20understand%20what,you%20are%20referring%20to)). 따라서 selection 상태도 하나의 상태로 간주하여 히스토리에 넣는 것을 권장합니다. 이때 **문제점**은 선택 영역 데이터를 어떻게 저장할 것인가입니다. 선택 영역은 이미지 크기의 마스크(픽셀 배열)일 수도 있으므로, 히스토리에 자주 넣기엔 부담입니다. 해결 방법:
  - 직사각형 선택이나 단순 형태는 좌표와 크기만 저장해도 되지만, 임의의 올가미 형태나 복잡한 마스크는 **마스크 텍스처 자체를 저장**해야 할 수도 있습니다. 이를 효율화하려면 **차분 저장**을 고려할 수 있습니다. 즉, "이전 선택영역에서 변경된 부분"만 저장하는 것입니다. 혹은 Selection도 Command 패턴으로 구현해서, `execute()`는 “선택 A를 이행”, `undo()`는 “이전 선택 B로 복귀” 형태로 하고, 내부적으로 B를 저장해두는 방식입니다.
  - Selection을 히스토리에 포함하지 않을 수도 있지만, 그러면 사용자가 편집 중 선택을 바꾼 뒤 Undo를 누르면 픽셀 변경만 되돌아가고 selection은 그대로라서 **맥락이 꼬일 수 있습니다**. 일관성을 위해서는 **selection도 상태의 일부**로 간주하는 게 좋습니다. 다만, 특정 경우(예: 이동툴로 레이어를 옮길 때 selection이 자동 해제되는 등)에는 히스토리에 남기지 않을 수도 있는데, 이런 세부 정책은 UX에 따라 결정하면 됩니다.
- **구현 난이도**: selection까지 포함한 히스토리는 구현이 다소 복잡하지만, 구조만 잘 잡으면 크게 어렵진 않습니다. 중요한 것은 **히스토리 시스템이 편집 대상의 다양한 상태(픽셀 데이터, 레이어 속성, 활성 툴, selection 등)** 중 **어디까지 관리할지 범위**를 명확히 하는 것입니다. 제안은:
  - **Document State** 객체를 만들고, 여기서 이미지의 모든 상태를 갖도록 합니다 (레이어 리스트, 각 레이어의 픽셀 데이터 or 텍스처, 현재 선택 마스크, 활성 툴 등). 그리고 히스토리는 이 Document State의 변화를 추적합니다.
  - Command 패턴을 쓰더라도, 각 Command의 undo 구현에서 필요하다면 Document State에 selection을 복원할 수 있도록 해야 합니다. 예컨대 “브러시로 그림” 커맨드를 undo할 때, 그 순간 selection 상태도 바뀌지 않도록, selection은 커맨드에 영향받지 않거나, 애초에 selection 변경 커맨드가 별도로 존재해야 합니다.
  - **Composite Command** 개념도 활용 가능: 특정 작업이 픽셀 변경 + selection 변경 두 가지를 동시에 일으키면 (예: 선택 영역을 이동하면 selection 바뀌고 이미지도 옮겨짐), 이를 하나의 복합 커맨드로 묶어 일괄 Undo/Redo 되도록 설계할 수 있습니다.
- **현재 구조의 대비**: 만약 현재 코드에 이미 Undo/Redo 스택 비슷한 것이 있다면, selection을 포함하고 있는지 확인해야 합니다. 또한, 히스토리 구현 시점에 **기존 모듈과의 결합도**를 점검해야 합니다. 히스토리를 나중에 붙이려 하면, 각 도구 모듈의 모든 상태 변화를 캡처해야 하므로 수정 범위가 넓어집니다. 가능하면 **초기부터 편집 작업은 반드시 HistoryManager를 통해서 수행**되도록 체계를 잡는 게 좋습니다. 이를테면, Canvas나 Layer 객체의 `drawPixel()` 같은 메서드를 직접 호출하지 말고, 항상 `HistoryManager.do(new DrawPixelCommand(...))` 이런 식으로 호출하게 강제하는 것입니다. 
- **UI 및 사용자 경험**: 히스토리가 들어가면 UI에 히스토리 패널 또는 Undo/Redo 버튼도 생길 것입니다. 이런 부분은 기능 구현과 함께 고려해야 하지만, 코드 구조 측면에서는 **HistoryManager를 전역(singleton 비슷하게)으로 두고** 각 기능 모듈이 이에 접근하도록 할지, 아니면 EditorCore가 HistoryManager를 포함하고 필요 시 커맨드를 전달하게 할지 결정해야 합니다. 후자가 모듈화를 유지하기 좋습니다.

**요약**: Undo/Redo 시스템은 편집기의 복잡도를 크게 높이므로, **초기에 아키텍처를 잘 잡고 들어가야 후환이 없습니다**. Selection 영역도 히스토리에 포함하는 것을 권장하며, 이를 위해 **Selection 상태를 객체화**하고 히스토리 스택에서 다룰 수 있게 설계합니다. 최종적으로 사용자는 Photoshop 등과 유사하게 selection 변경까지 Undo로 돌릴 수 있어야 직관적입니다 ([Adobe software undo selection - Graphic Design Stack Exchange](https://graphicdesign.stackexchange.com/questions/77286/adobe-software-undo-selection#:~:text=I%20do%20not%20understand%20what,you%20are%20referring%20to)). 구조적으로는 Command 패턴 기반으로 구현하고, Document State 개념으로 포괄적인 상태 관리를 하는 방향을 추천합니다.

## 향후 기능 확장을 고려한 구조 개선
질문에서 제시한 앞으로 구현 예정 기능들 – **플러드 필(Flood fill)**, **레이어 시스템(블렌딩 포함)**, **DB 저장 구조**, **국제화(i18n)**, **SEO** 등 – 을 염두에 두고, 현재 구조의 잠재적 한계와 바람직한 개선 방향을 정리합니다.

### 1. 플러드 필(Flood Fill) 구현 대비
Flood fill(페인트 통(bucket)으로 인접 영역 채우기)은 구현 난이도가 있는 기능입니다. **구조적인 관점**에서 미리 준비할 점은:
- **알고리즘 선택**: 단순하게는 재귀나 큐(BFS)를 돌며 픽셀을 채우는 CPU 알고리즘이 있지만, 이는 큰 이미지에서 **성능상 위험**이 큽니다 (재귀는 call stack 위험도). 대신 **스캔라인 알고리즘**으로 반복을 줄이거나, **JS 워커**에서 BFS를 돌리도록 해야 합니다. 최선은 **GPU로 병렬 flood fill**을 수행하는 것인데, WebGL에서는 일반 재귀는 못하지만 **Jump Flood Algorithm (JFA)** 등을 응용할 수 있습니다 ([Instant flood fill with HTML Canvas - Hacker News](https://news.ycombinator.com/item?id=36049386#:~:text=Instant%20flood%20fill%20with%20HTML,the%20complexity%20is%20often)). JFA는 GPU 셰이더에서 병렬로 거리를 확장하며 채우는 알고리즘으로, Canvas 2D flood fill보다 월등히 빠릅니다 ([Instant flood fill with HTML Canvas - Hacker News](https://news.ycombinator.com/item?id=36049386#:~:text=Jump,the%20complexity%20is%20often)). 다만 구현 복잡도가 있으니, 처음에는 워커 기반 CPU 알고리즘으로도 괜찮습니다. 중요한 것은, **Flood fill도 Tool의 하나로 취급**하여 Tool 모듈로 분리하고, 결과 픽셀 변경을 history command로 기록하는 구조입니다.
- **데이터 접근**: Flood fill은 픽셀의 색상 비교를 많이 합니다. 현재 캔버스 데이터가 GPU 텍스처에만 있고 CPU에서 접근 불가능하다면, **텍스처 데이터를 읽어올 방법**이 필요합니다. WebGL에서는 `gl.readPixels()`로 텍스처 데이터를 가져올 수 있지만 매우 느립니다. 차라리 **캔버스 2D 컨텍스트**에서 `getImageData` 하거나, OffscreenCanvas에 그려두고 `ImageData`를 가져오는 편이 나을 수 있습니다. 또는, 유지보수 구조 측면에서 **메인 Canvas의 Pixel Array를 항상 유지**하는 방법도 있습니다. 예를 들어 모든 그리기 연산 시 WebGL 텍스처 업데이트와 동시에, 동일 내용을 가진 Uint8Array를 갱신해 두는 것입니다. 그러면 flood fill은 그 배열을 가지고 워커에서 돌린 후, 결과를 WebGL 텍스처에 적용하면 됩니다. 이중 유지라 메모리 소모는 있지만, GPU-CPU 동기화 비용을 줄여줍니다.
- **워커 활용**: 위에서 언급했듯 flood fill은 워커에 맡기는 게 좋습니다. **현재 구조에 워커가 없다면**, flood fill 구현 시점에 워커 아키텍처를 도입하게 될 것이므로, **지금 미리 워커 통신 구조를 잡아두는 것**이 도움이 됩니다. 예컨대 WorkerManager 모듈을 만들어놓고, 나중에 어떤 연산이든 쉽게 워커 실행->Promise 반환 형태로 쓸 수 있게 해두면, flood fill뿐 아니라 다른 기능도 활용할 수 있습니다.
- **실시간 미리보기**: flood fill은 보통 한 번 클릭하면 바로 완료되는 작업이라 미리보기 개념은 없지만, tolerance(색상 포용 범위) 등의 옵션을 조절할 경우 미리 하이라이트를 표시할 수 있습니다. 구조적으로 **Flood fill Tool**을 설계할 때 이러한 옵션과 UI 연계를 생각해야 합니다. Tool 모듈에 옵션 필드를 두고 UI에서 변경하면 툴의 내부 상태가 바뀌고, 필요하면 미리 연산을 다시 하는 흐름입니다. 즉, 툴을 단순 함수로 짜지 말고 **상태ful 객체**로 만들어두면 확장이 쉽습니다.

요약하면, **Flood fill 도구는 Worker와 GPU를 연계하여 고속으로 구현**하되, 초기엔 CPU 워커로 시작해도 됩니다. 핵심은 현재 구조에서 flood fill이 **독립된 모듈**로 추가될 수 있는지, 그리고 **캔버스 픽셀 데이터 접근 경로**가 마련되어 있는지입니다. 없다면, 이를 대비해 Pixel 데이터를 관리/공유하는 구조 개선이 필요합니다.

### 2. 레이어 시스템 (Layers & Blending)
레이어 기능은 단일 캔버스를 넘어 **여러 개의 겹쳐진 캔버스** 개념을 도입하는 것으로, 코드 구조에 큰 변화를 요구합니다. 이를 고려한 제언은 다음과 같습니다:
- **Layer 클래스 도입**: 각 레이어를 표현하는 `Layer` 클래스를 정의합니다. 이 클래스는 **픽셀 데이터 또는 WebGL 텍스처**, **가시성(visible)**, **투명도(opacity)**, **블렌딩 모드(blend mode)** 등의 속성을 갖습니다. Editor는 다수의 Layer 인스턴스를 보유하고, **현재 활성 레이어** 포인터를 유지합니다.
- **블렌딩 구현**: WebGL을 쓰고 있으므로, **블렌딩 모드** 구현은 비교적 수월합니다. Photopea의 사례에서 WebGL을 활용해 *“모든 블렌드 모드에 GPU 가속 적용”*을 했다고 하는데 ([  Photopea 1.3](https://blog.photopea.com/photopea-1-3.html#:~:text=Pixel%20data%20of%20each%20layer,use%20hadrware%20acceleration%20also%20for)), 우리도 각 레이어 텍스처를 합성하는 **Fragment Shader**를 작성하면 됩니다. WebGL 내장 블렌딩(알파블렌딩 등 기본)은 `gl.BLEND`로 어느 정도 지원하지만, Multiply, Screen, Overlay 등 Photoshop류의 블렌딩은 custom shader로 구현해야 합니다. 구조적으로, **Renderer**가 모든 레이어를 순서대로 그리도록 변경해야 합니다. 예전에는 하나의 캔버스에 직접 그리던 것을, 이제는 레이어 N개를 돌면서 가장 아래 레이어부터 상위 레이어까지 누적 렌더링하는 방식입니다. 각 레이어별로 블렌딩 모드에 따라 다른 shader/연산을 해야 할 수 있으므로, Renderer가 그 책임을 져야 합니다.
- **성능 고려: 합성 방식**: 레이어가 많아지면 매 프레임 모든 레이어를 다 그리면 비효율적입니다. 한편, 이미지 에디터에서는 **레이어 내용이 자주 바뀌지 않으면** 합성 결과를 캐시할 수 있습니다. 예를 들어, 5개의 레이어 중 아래 4개는 안 바뀌고 최상위 레이어만 변경 중이라면, 아래 4개 합성 결과를 미리 FBO에 저장해두고 최상위 레이어만 합성하면 됩니다. 이런 **스마트 렌더링**을 하려면 레이어에 변경 플래그(dirty flag)를 두고 관리하는 등 추가 로직이 필요하지만, MAU 100만 명 서비스를 생각하면 최적화를 염두에 두는 게 좋습니다. 현재 구조에서 단일 캔버스만 다루고 있다면, 다층 구조로 변경하면서 이러한 최적화 여지를 남겨두길 권장합니다.
- **UI 및 사용자 조작**: 레이어 추가/삭제, 순서 변경, 복제, 병합 등 다양한 기능이 추가될 텐데, 이는 주로 **UI 레이어 패널 모듈**과 **LayerManager** 모듈로 처리합니다. LayerManager는 내부 데이터 구조를 변경하고 Renderer에 알려줘서 다시 그리게 하며, History에도 추가합니다. 이처럼 레이어 추가로 인해 **Editor의 중심축이 LayerManager**로 이동하게 되므로, 초기 구조를 잡을 때 EditorCore 내에 LayerManager(또는 layers array)를 포함시켜 두면 이후 통합이 쉽습니다. 
- **현재 코드에의 영향**: 만약 현재 대부분의 도구 코드가 "canvas에 직접 그린다"는 가정으로 작성되었다면, 레이어 도입 시 이를 "현재 활성 레이어에 그린다"로 변경해야 합니다. 미리 이를 추상화하려면, 도구들이 canvas나 gl 컨텍스트를 직접 쓰지 않고 LayerManager 또는 Renderer를 통해서 그리게 만들어야 합니다. 그러면 나중에 Renderer가 내부적으로 활성 레이어 텍스처를 잡도록 바꿀 수 있습니다. 
- **파일 저장 구조와 연계**: 레이어가 생기면, 저장할 때 단순 PNG/JPEG 외에 **프로젝트 저장 포맷**이 필요해집니다. 자체적으로 JSON+이미지들로 저장하거나, PSD 호환으로 갈 수도 있습니다. 이 점은 다음 **DB 저장 구조**와도 관련되므로 함께 고려해야 합니다.

### 3. DB 저장 구조 (백엔드 연동 및 저장)
1백만 사용자 서비스를 운영하려면, 편집 결과물이나 프로젝트를 **DB에 저장**하고 불러오는 기능이 필연적입니다. 현재는 아마 **로컬에서만 동작하는 에디터**겠지만, 추후 **사용자별 클라우드 저장, 작품 공유** 등이 필요할 수 있습니다. 이를 위한 구조 제안:
- **저장 대상과 형태**: 우선 무엇을 저장할지 결정해야 합니다. 완성된 이미지(jpeg/png)만 서버에 저장할 것인지, 아니면 **편집 가능한 프로젝트 상태(레이어, 히스토리 등)**를 저장할 것인지입니다. 둘 다 필요할 가능성이 높습니다. 프로젝트 상태 저장을 위해, 앞서 언급한 **Document State**를 직렬화(serialize)하는 기능이 필요합니다. 이를 JSON으로 표현하거나, 또는 특정 바이너리 포맷(PSD나 자체 binary)을 정할 수 있습니다. 구조적으로 Document State 객체에 `toJSON()`이나 `serialize()` 메서드를 구현해 두면, 쉽게 직렬화하여 IndexedDB나 서버 API로 보낼 수 있습니다.
- **로컬 저장 vs 서버 저장**: 1) **IndexedDB/LocalStorage** 등을 이용해 브라우저에 저장: 오프라인 작업이나 빠른 자동저장에 유용. 2) **원격 서버 API**로 저장: 계정별 관리나 여러 기기 간 동기화에 필요. 두 가지를 모두 고려해야 하는데, **저장 모듈을 추상화**해서 구현하면 동일 인터페이스로 둘 다 지원하기 편합니다. 예: `StorageProvider` 인터페이스를 만들어 `LocalStorageProvider`, `RemoteStorageProvider` 등의 구현을 두고, 상황에 따라 선택.
- **DB 스키마**: 서버에 저장한다면, 백엔드 DB에 어떤 식으로 데이터를 넣을지 생각해야 합니다. 대용량 이미지 바이너리를 다루므로 **대용량 파일 저장**은 Object Storage(예: AWS S3) 등을 쓰고, 메타데이터나 JSON은 일반 DB에 넣는 식으로 구분 가능할 것입니다. 이 부분은 프론트엔드 코드 구조와 직접적 연관은 없지만, API 호출을 위해 **비동기 통신 모듈**을 만들고, 프로젝트 save/load 시 UI를 잠그거나(progress) 하는 처리를 프론트 구조에 녹여내야 합니다.
- **자동 저장과 히스토리**: 편집 도중 주기적으로 자동저장을 한다면, 히스토리 상태를 같이 저장할지도 고려해야 합니다. 단, 히스토리까지 저장하면 용량이 커질 수 있어서, 보통 **저장 시에는 현재 상태만 저장**하고 히스토리는 복원하지 않습니다. 이 정책을 결정하고 구현에 반영해야 합니다.
- **권한 및 동시 편집**: 만약 협업 편집을 생각한다면 (여러 사람이 동시에 편집), 이는 훨씬 복잡한 실시간 동기화 구조(Operational Transform 또는 CRDT 등)를 요구합니다. 질문 범위를 벗어나므로, 현재는 **단일 사용자 편집 세션 저장**만 상정하고 구조를 짜면 될 것 같습니다. 
- **현재 구조 대비**: 백엔드 연동이 전혀 없는 상태라면, 우선 **API 통신 레이어**를 별도로 구성하는 것이 좋습니다. 예컨대 `api.js` 혹은 `ProjectService` 클래스를 만들어 HTTP 요청을 담당하게 하고, Editor 모듈은 이 서비스를 호출만 하도록 분리합니다. 이렇게 하면 훗날 API가 변경되거나 클라이언트를 변경해야 할 때 영향 범위가 작아집니다. 또한 저장/불러오기 중에는 편집을 막거나 진행 상황을 보여줘야 하므로, **에디터 상태**에 "loading/saving" 같은 플래그를 두고 UI와 연동하면 됩니다 (예: React라면 state로 처리하겠지만, 바닐라라면 이벤트나 콜백으로 처리).

### 4. 국제화(i18n) 구조
다국어 지원은 비교적 국소적인 변경이지만, **초기에 준비**해두면 추후 수백 개 문자열을 일일이 바꾸는 수고를 덜 수 있습니다. i18n을 위해 고려할 점:
- **리소스 관리**: 모든 UI 텍스트를 코드에서 하드코딩하지 말고 **별도 리소스 파일(JSON 또는 JS객체)**로 분리합니다. 예: `locales/en.json`, `locales/ko.json` 등으로 각 언어별 번역 문자열을 키-값 쌍으로 저장. 그러면 언어 전환도 리소스 교체로 쉽게 할 수 있습니다. 현재 구조가 바닐라 JS라면, 간단히 `const STRINGS = { en: {...}, ko: {...} }` 객체를 만들어 써도 되고, 규모가 커지면 i18next 같은 라이브러리를 붙일 수도 있습니다.
- **코드 수정**: UI에 표시되는 부분(툴 이름, 메뉴, 안내문구 등)을 모두 해당 리소스에서 가져오도록 수정해야 합니다. 예컨대 `document.getElementById('btnUndo').title = STRINGS[currentLang].undo;` 이런 식으로. 이를 체계화하려면 **간단한 i18n 함수**를 만들어 `t(key)`로 쓰게 해도 됩니다.
- **동적 변경**: 사용자 언어 변경을 지원하려면, UI를 다시 렌더링하거나 텍스트 노드를 업데이트해야 합니다. 프레임워크 없이 구현하려면 모든 UI 요소를 가리키는 참조를 들고 있다가 언어 변경 이벤트 시 각각 텍스트를 갈아끼우는 식이 될 겁니다. 약간 번거롭지만, 구조적으로는 UI 초기화 로직을 한 곳에 모아두면 나중에 `updateLanguage(lang)` 함수를 만들어 재사용할 수 있습니다.
- **숫자/날짜 등**: 주로 텍스트 위주이겠지만, 혹시 색상 포맷이나 단위, 날짜가 들어갈 경우 locale에 맞게 표시해야 합니다. JS Intl API 등을 활용할 수 있으나, 현재는 크게 해당 사항 없을 것 같습니다.
- **Test & Fallback**: i18n 적용 후에도 기본이 영어이거나 하고, 새 언어 추가 시 일부 키가 누락되면 기본 언어나 키 그대로 나오게 하는 등 **폴백 처리**도 고려합니다.
- **SEO와의 관계**: 다국어 지원은 SEO에도 영향이 있습니다. SSR을 도입한다면 서버측에서 각 언어 페이지를 만들어 낼 수 있지만, CSR만 있다면 구글봇이 JS 실행해야 번역된 내용이 나오겠죠. 이 부분은 후술할 SSR에서 함께 고려됩니다.

### 5. SEO 및 SSR 대응
SEO(Search Engine Optimization)를 고려한다는 것은, 이 프로젝트가 단순한 웹앱이 아니라 **검색 엔진에 노출될 만한 컨텐츠를 생산하거나, 마케팅 페이지가 존재**한다는 의미로 보입니다. 캔버스 기반 웹앱은 그 자체로는 SEO에 큰 의미가 없지만, 예를 들어 **사용자가 만든 이미지를 공유하는 갤러리**, **튜토리얼 페이지**, **다운로드 페이지** 등이 있다면 SEO가 중요해집니다. 또한 SSR(Server-Side Rendering)은 SEO 외에 초기 로딩 성능 때문에도 도입을 고려할 수 있습니다. 현재 **바닐라 JS + Canvas** 구조에서 **CSR->SSR 전환**을 고려하려면:
- **SSR이 필요한 부분 식별**: 에디터 캔버스 자체는 **DOM 노드가 거의 없고** <canvas>만 있으므로 SSR로 얻을 이득이 적습니다. SSR은 HTML 컨텐츠를 미리 뿌려주는 것이기 때문에, 이미지 에디터처럼 내용이 canvas로 그려지는 앱에서는 SEO 봇이 볼 수 있는 텍스트가 거의 없습니다. **따라서, 에디터 웹앱 자체는 SSR 필요성이 낮고 오히려 CSR이 적합**합니다 (상호작용과 성능 측면) ([Render Wars: “SSR” || “CSR” in Web Application Architectures. | by Mostafa Ibrahim | Medium](https://medium.com/@imostafax/render-wars-ssr-csr-in-web-application-architectures-98bdca1c0fd9#:~:text=Client)) ([Render Wars: “SSR” || “CSR” in Web Application Architectures. | by Mostafa Ibrahim | Medium](https://medium.com/@imostafax/render-wars-ssr-csr-in-web-application-architectures-98bdca1c0fd9#:~:text=,Consistent%20Rendering)). 그러나 **부가적인 정적 페이지**(홈페이지 소개, 가이드, 블로그 등)는 SSR/정적생성으로 만들어 SEO를 높일 수 있습니다.
- **혼합 전략**: 많은 현대 웹앱이 **SSR + CSR 혼합**으로 가는데, Next.js 같은 프레임워크를 쓰면 일부분 SSR하고, 편집기 같은 부분은 CSR로 동작하게 구성할 수 있습니다. 예를 들어 `/editor` 경로는 CSR 전용 React 페이지로 두고, `/`, `/about`, `/gallery` 등은 SSR로 렌더링하는 식입니다. 현재 바닐라 JS 구조에서는 곧장 Next.js로 옮기긴 부담일 수 있으나, **UI 계층을 점진적으로 프레임워크로 교체**하는 방법이 있습니다. 
  - 예: 캔버스와 툴바, 메뉴 등을 React나 Svelte로 포팅하고, 그 내부에서 기존 EditorCore를 호출하도록 하면, UI는 SSR이 가능해집니다. 다만 WebGL context는 SSR 시 생성 불가이므로, 실제 canvas 그리기는 CSR 단계에서만 이뤄져야 합니다. 이를 위해 **컴포넌트 마운트 후 초기화**하는 구조로 작성하면 될 것입니다.
- **바닐라 JS에서의 SSR 방안**: 프레임워크를 쓰지 않고 SSR 비슷하게 하려면, **서버에서 초기 HTML 파일을 만들어주는 정도**를 생각할 수 있습니다. 예컨데 Node.js로 템플릿을 돌려 `<title>`, `<meta>`태그나 간단한 구조만 넣어서 보내주고, 이후 JS가 로딩되어 앱을 부트스트랩하는 방식입니다. 이것도 일종의 SSR이지만, 실제 UI를 그리는 건 클라이언트 JS라 SEO에는 한계가 있습니다. 검색엔진 크롤러가 기본적으로 Canvas 내용은 이해 못하니, 편집기 자체는 SEO 연관성이 낮죠. 다만 **앱 설명, 제목, 키워드** 등을 HTML에 미리 넣어두는 건 중요합니다.
- **SEO 고려사항**: 만약 이 서비스에서 **유저가 만든 이미지를 페이지로 공유**하는 기능이 있다면, 그 페이지에 캔버스가 아닌 **<img> 태그와 함께 <meta> 정보**(제목, 설명 등)를 삽입하여 SEO에 걸리게 해야 합니다. SSR이라면 사용자가 만든 콘텐츠 페이지를 정적으로 생성하거나, 서버에서 데이터를 받아 HTML로 뿌려주는 게 가능할 겁니다. 
- **SSR 전환 시기**: 개인 프로젝트 단계에서 너무 이른 SSR 도입은 개발 복잡도를 높입니다. 우선 제품 기능 개발과 구조 개선이 더 급선무이고, SEO/SSR은 사용자가 늘고 **마케팅/검색 유입을 본격적으로 늘리고자 할 때** 도입해도 늦지 않습니다. 다만, **코드 구조는 SSR을 염두에 두고 작성**하면 추후 전환이 수월합니다. 예를 들어, DOM 조작이나 전역 접근을 최소화하고, 상태를 명시적으로 관리하면 React/Svelte 등으로 마이그레이션하기 편합니다.

**요약**: SEO와 SSR은 주로 **웹사이트의 목적**에 따라 결정됩니다. 에디터 자체는 CSR로 남겨두고 주변 사이트를 SSR/정적화하는 혼합 접근을 권장합니다. 현재 바닐라 구조에서는 곧바로 SSR 적용은 어려우므로, 대신 **메타태그 관리, 초기 로딩 화면 제공** 등 작은 개선부터 하고, 중장기적으로는 UI를 프레임워크 기반으로 재구성해 SSR을 도입하는 방안을 생각해볼 수 있습니다. 중요한 것은, **SSR을 염두에 두고 모듈화**하는 것입니다. UI와 상태/로직이 분리되어 있으면, 나중에 어떤 렌더링 방식이든 유연하게 대응할 수 있습니다.

## 구조적인 위험 요소 및 리팩토링 권장 시점
앞서 분석한 내용을 바탕으로, 현 코드 구조의 **위험 요인**과 **향후 확장에 불리한 부분**을 요약하고, **리팩토링 시기** 및 필요 시 **재설계(엎기)** 판단에 대해 언급합니다:

- **복잡도 급증 위험**: 현재는 단일 캔버스, 단일 이미지 상태로 동작하지만, 레이어, 히스토리 등이 들어가면 코드 복잡도가 기하급수적으로 늘어납니다. 만약 **초기에 구조를 잡아두지 않으면** 신규 기능을 추가할 때마다 많은 부분을 수정해야 하고, **사이드 이펙트**로 버그가 발생하기 쉽습니다. 특히 히스토리와 레이어는 편집기 아키텍처를 크게 바꾸므로, 이러한 기능을 공식 출시 목표로 한다면 **리팩토링을 미루지 말고 초기에 실시**하는 것이 좋습니다. 구체적으로, **Undo/Redo와 Layer의 기본 틀**을 먼저 만들어두고 브러시/지우개 등의 기존 기능을 거기에 얹는 식으로 재구성하는 것을 권장합니다.
- **성능 병목 및 구조적 한계**: 앞서 언급한 GPU 메모리 관리, readPixels 사용, 메인스레드 블로킹 등의 이슈는 **구조적으로 해결해야 하는 성능 병목**입니다. 사용자가 적을 땐 간과되겠지만 100만 명 규모에선 다양한 사용 패턴이 나오고, 엣지 케이스(ultra high resolution image, 아주 잦은 undo/redo 등)에서 문제가 터질 수 있습니다. 이러한 부분은 **코드 프로파일링과 부하 테스트**를 통해 미리 찾아내고, 구조를 보완해야 합니다. 예컨대 히스토리를 구현할 때 메모리 사용이 많아질 것을 대비해 **최대 히스토리 개수**를 정하고, 오래된 히스토리는 버리거나 디스크 캐싱하는 등 정책도 정해야 합니다.
- **모듈 간 결합도**: 현재 구조에서 모듈 분리가 미흡한 부분이 그대로 두면, **기능 확장시 결합도 높은 모듈들이 서로 얽혀 변경하기 어려운 구조**가 될 우려가 있습니다. 예를 들어 Tool과 Renderer가 강하게 결합돼 있으면 레이어 도입 시 둘 다 갈아엎어야 할 수 있습니다. 따라서 **결합도를 낮추는 방향으로 지속적인 리팩토링**이 필요합니다. 구체적 방법은 인터페이스/추상 클래스 도입, 이벤트/구독 패턴 도입(툴이 Renderer에 신호만 보내고 Renderer가 처리하게) 등이 있습니다.
- **재설계(엎기) 필요 여부**: 만약 코드가 이미 상당히 복잡하고 난개발되었다면, **일부 핵심 컴포넌트는 아예 다시 작성**하는 것이 나을 수도 있습니다. 예를 들어, 
  - 기존에 히스토리 고려 없이 직접 canvas 조작하는 함수들이 많다면, **HistoryManager 도입과 함께 drawing API들을 전면 교체**해야 합니다.
  - 레이어 개념이 전혀 없는 코드라면, 이를 덧붙이는 것보다 **Canvas 관리 부분을 새로 작성**해서 기존 코드와 교체하는 식으로 진행할 수 있습니다.
  - Vanilla JS로 만든 UI가 복잡해지고 버그가 많다면, 과감히 React/Svelte 등의 도입을 고려해볼 수 있습니다. 초기 투자 비용은 있지만, 길게 보면 개발 생산성과 유지보수성이 향상됩니다.

  **엎어야 할 시점**은, 기존 코드 수정이 새로운 코드 작성보다 어려워지는 지점입니다. 다행히 현재 프로젝트는 아직 기능 추가 단계에 있으므로, **선제적으로 구조 개편**을 하면 전체를 엎지 않고도 개선 가능해 보입니다. 하지만 향후 일정상 여유가 있고 코드 이해도가 높다면, 특정 서브시스템(예: 히스토리+레이어 부분)은 아예 **별도의 브랜치에서 새로 설계/구현**한 뒤 기존 코드와 통합하는 방식을 추천합니다.
- **리팩토링 단계적 진행**: 모든 것을 한 번에 리팩토링하는 것은 위험하므로, 단계를 나눠 진행합니다. 
  1. **모듈화 1단계**: 파일 구조 정리 및 클래스 도입 (툴별 클래스, 렌더러 클래스, 매니저류 도입). 이 과정에서 기존 동작은 유지하면서 코드 이동/분리를 합니다.
  2. **히스토리/커맨드 패턴 도입**: 가장 큰 구조 변화입니다. 이 단계에서는 내부 동작을 Command 형태로 바꾸고, Undo/Redo는 UI에서 누르지 않아도 내부적으로 동작하게(아직 노출 안 해도) 만들어 놓습니다.
  3. **레이어 구조 도입**: 히스토리가 어느 정도 자리잡으면 레이어를 추가합니다. 처음엔 1개 레이어로 동작하지만 구조상 레이어 배열을 쓰도록 변경하고, Renderer가 레이어를 loop 돌도록 수정합니다. 그리고 서서히 UI에서 다중 레이어를 켜주는 식으로 확장합니다.
  4. **성능 튜닝 및 워커 도입**: 위 기능들이 동작하면, 병목이 되는 부분을 찾아 워커로 분산하거나 OffscreenCanvas 적용, 셰이더 최적화 등을 합니다. 이때는 사용자 피드백이나 메모리/CPU 프로파일을 기반으로 진행합니다.
  5. **부가 기능**: 국제화, 저장, SEO 대응 등을 마지막에 붙입니다. 국제화는 비교적 어디서든 할 수 있지만, UI 변경이 많을수록 나중에 하는 게 중복 작업을 줄입니다. SEO/SSR은 제품 안정화 후 별도 프로젝트로 진행해도 될 만큼 핵심 로직과는 분리해 생각해도 됩니다.
- **기술 부채 관리**: 이미 인지한 현재 구조의 문제(예: ~~기능이 하드코딩되어 있다~~, ~~전역변수가 많다~~ 등)들은 **기술 부채로 리스트업**해두고, 주기적으로 상쇄하도록 합니다. 예를 들어 "FIXME" 주석이나 깃허브 이슈로 만들어두고 다음 개발 스프린트에 일정 시간을 배정해 해결하는 식입니다. 이렇게 하면 프로젝트가 커져도 코드 품질을 일정 수준 유지할 수 있습니다.

## 결론 및 핵심 개선 요약
요약하면, 현 WebGL2 기반 픽셀 에디터 프로젝트는 **기능 구현은 잘 되어 있으나 대규모 확장에 대비한 구조적 보강이 필요**한 상태입니다. 모듈 분리, 책임 분할, 히스토리/레이어 등의 설계를 미리 준비해두는 것이 장기적으로 개발 효율을 높이고 100만 MAU 환경에서도 안정적인 서비스를 제공하는 열쇠입니다. 아래 핵심 개선 사항을 bullet point로 정리합니다:

- **모듈화 및 아키텍처 개선**: UI, 렌더링, 도구 로직, 데이터/상태 관리 모듈을 명확히 분리하고, 커맨드/이벤트 패턴 등을 도입해 **낮은 결합도**와 **높은 응집도**를 달성합니다.
- **툴 및 렌더링 구조 정비**: 각 툴을 공통 인터페이스로 리팩토링하고, **Renderer(렌더링 매니저)**가 모든 그리기를 제어하도록 구조를 개선합니다. WebGL 셰이더/텍스처 관리도 중앙화하여 **신규 효과나 최적화 적용이 용이**하게 만듭니다.
- **WebGL 성능 최적화 준비**: GPU 메모리 한계, CPU-GPU 데이터 복사 최소화, 다중 렌더링 시나리오를 고려해 **OffscreenCanvas 등 최신 기술**을 활용할 수 있게 코드 구조를 유연하게 유지합니다 ([OffscreenCanvas—speed up your canvas operations with a web worker  |  Articles  |  web.dev](https://web.dev/articles/offscreen-canvas#:~:text=Moving%20heavy%20calculation%20to%20a,on%20the%20source%20canvas%20automatically)). 저사양 기기 호환과 fallback 경로도 마련해둡니다.
- **워커 도입 및 비동기 처리**: 무거운 연산은 **Web Worker로 오프로드**하고, 메인 스레드와의 통신 체계를 구축합니다. 향후 Undo/Redo와 연동하여 비동기 작업도 히스토리에 일관되게 포함될 수 있도록 **작업 큐와 완료 핸들링 구조**를 설계합니다.
- **Undo/Redo (History) 시스템 구현**: **Command 패턴 기반의 히스토리 관리자**를 도입하여 모든 편집 작업을 추적합니다. Selection 변화도 Undo 대상에 포함시켜 **편집 상태의 완전한 역사**를 관리합니다 ([Adobe software undo selection - Graphic Design Stack Exchange](https://graphicdesign.stackexchange.com/questions/77286/adobe-software-undo-selection#:~:text=I%20do%20not%20understand%20what,you%20are%20referring%20to)). 메모리 효율을 위해 필요 시 **부분 스냅샷**이나 **diff**만 저장하는 전략을 적용합니다.
- **Flood Fill, 레이어, 기타 기능 대비**: Flood fill은 **워커+GPU** 활용을念頭に置いて実装し, 레이어 시스템은 **Layer 객체와 Renderer 개선**을 통해 자연스럽게 도입할 수 있게 미리 Canvas 관리 코드를 일반화합니다. 레이어의 블렌딩은 GPU로 처리하여 성능을 확보하고 ([  Photopea 1.3](https://blog.photopea.com/photopea-1-3.html#:~:text=Pixel%20data%20of%20each%20layer,use%20hadrware%20acceleration%20also%20for)), 레이어 추가에 따른 UI/저장 구조 변경도 함께 설계합니다.
- **데이터 영속화 및 서비스화**: 프로젝트 저장/불러오기를念頭に置き、**직렬화/역직렬化** 인터페ース를 정의합니다. 추후 **백엔드 API 연동 모듈**을 분리 구현하고, 저장 중 UI 상태 관리 등의 로직을 메인 흐름과 분리하여 유지보수성을 높입니다.
- **국제화(i18n)**: UI 문자열을 리소스 파일로 분리하고, 다국어 지원을 쉽게 추가할 수 있는 구조로 개편합니다. 초기부터 키 기반으로 문자열을 넣으면 추후 번역 작업이 수월합니다.
- **SEO 및 SSR 전략**: 에디터 앱 핵심은 CSR로 유지하되, **주변 정적 컨텐츠는 SSR/정적 배포**를 활용하는 혼합 전략을 취합니다. 코드 구조를 SSR-friendly하게 작성(상태와 뷰 분리)하면, 필요 시 React/Vue 등의 도입과 SSR 전환이 비교적 쉬워집니다. 우선은 **메타데이터 관리**와 **초기 로딩 최적화**에 집중하고, 사용자 증가에 따라 SSR 도입 여부를 결정합니다 ([Render Wars: “SSR” || “CSR” in Web Application Architectures. | by Mostafa Ibrahim | Medium](https://medium.com/@imostafax/render-wars-ssr-csr-in-web-application-architectures-98bdca1c0fd9#:~:text=Server,page%20to%20the%20client%E2%80%99s%20browser)).
- **리팩토링 타이밍**: 핵심 아키텍처 (히스토리, 레이어 등)는 **가능한 이른 시기에 구축**하고, 이후 기능을 얹는 방식으로 개발을 진행합니다. 현재 구조에서 크게 변경해야 하는 부분은 단계별로 리팩토링을 수행하여 리스크를 낮춥니다. 필요한 경우 일부 컴포넌트는 **재설계**도 주저하지 말고 수행하여, **기술 부채**를 초기 단계에서 해소합니다.
- **레거시/호환 고려**: 100만 사용자 중에는 다양한 브라우저/환경이 있을 것이므로, **WebGL2 미지원 시 대처**, **모바일 터치 UX 개선**, **Accessibility(접근성)** 등도 구조 개선 로드맵에 포함하면 좋습니다. 이러한 비기능 요구 사항도 추후 확장에 영향을 주므로, 미리 확장 포인트를 마련해둡니다.

마지막으로, **"지금 구조를 그대로 두고 기능 개발을 이어가는 것"**과 **"일부를 엎고 가는 것"** 사이에서 고민된다면, **장기적 안목에서 유연한 구조를 갖추는 쪽으로 투자**하길 권합니다. 초기 사용자 확보도 중요하지만, **확장에 불리한 구조를 안고 성장하면 나중에 속도 저하와 품질 문제**로 더 크게 대가를 치르게 됩니다. 차근차근 구조를 개선해나가면, 향후 어떤 기능 추가 요구에도 견딜 수 있는 탄탄한 편집기 플랫폼으로 발전할 것입니다. 개발자로서도 새로운 기능 구현에 더 집중할 수 있고, 협업이 늘어나도 코드 이해가 수월한 체계를 갖추게 될 것입니다.以上の提案を踏まえて 리팩토링 로드맵을 작성하고 하나씩 개선해 나가면, 궁극적으로 **유연하고 확장 가능한 웹 기반 그래픽 에디터**를 실현할 수 있을 것으로 기대됩니다.
